# NexusSlate v0.19 GPU Docker images and Unraid deployment

v0.19 adds a GPU-capable Docker image variant and a Community Applications
deployment path for Unraid. Neither changes what hardware acceleration Go
code decides to use — that detection and fallback logic is unchanged (see
[hardware-accelerated derived media](../README.md#hardware-accelerated-derived-media)).
What changes is what's available *inside the container* for it to detect.

## The two image tags

`Dockerfile` builds two runtime variants from the same source:

| `docker build --target …` | Contains | Use it for |
| --- | --- | --- |
| *(no target — default)* | `ffmpeg`, `ffprobe`, `exiftool` only, same as v0.18 | CPU/software encode, macOS Docker Desktop with no passthrough, or any host where hardware acceleration isn't wired up |
| `gpu` | The default image plus the VAAPI userspace for Intel/AMD iGPUs | A Linux host — bare metal, VM with PCI passthrough, or Unraid — with `/dev/dri` and a device-passthrough stanza enabled |

```sh
docker build -t nexusslate:v0.19 .                    # unchanged, CPU/software
docker build --target gpu -t nexusslate:v0.19-gpu .    # + VAAPI userspace
```

A plain `docker build` with no `--target` still produces the CPU image —
the Dockerfile ends with an explicit alias stage to guarantee that, since
Docker otherwise builds whichever stage is textually last in the file.

**NVIDIA needs nothing baked into either image.** Debian bookworm's stock
`ffmpeg` package already ships `h264_nvenc`/`hevc_nvenc`. NVENC only fails
inside a container because the *runtime* libraries
(`libnvidia-encode.so.1`, `libcuda.so.1`) and device nodes have to come from
the host, injected by the NVIDIA Container Toolkit and matched exactly to
the host's loaded kernel module. Baking any NVIDIA `.so` into the image
would be a version-skew trap the moment the host driver updates — so NVIDIA
support is pure compose/template wiring, never a Dockerfile package, and
both image variants work with it identically.

## What the `gpu` target actually installs

Intel and AMD both go through the same Linux DRM render node
(`/dev/dri/renderD128`) via libva — Mesa's `radeonsi` serves AMD,
`intel-media-va-driver`'s `iHD` serves Intel — so one image variant covers
both vendors.

`debian:bookworm-slim`'s default `/etc/apt/sources.list.d/debian.sources`
(deb822 format) enables only the `main` component:

```
Types: deb
URIs: http://deb.debian.org/debian
Suites: bookworm bookworm-updates
Components: main
Signed-By: /usr/share/keyrings/debian-archive-keyring.gpg
```

`intel-media-va-driver-non-free` lives in Debian's `non-free` component,
which isn't on by default, so the `gpu` stage enables it with `sed` before
installing anything. Every driver package is then installed **one at a
time and allowed to fail individually** — the same pattern
`deploy/prepare-node.sh` already uses for the same reason: these package
names, and which archive component carries them, differ across Debian
releases and get renamed often enough that a single missing name must not
take the rest of the `apt-get` transaction down with it.

| Package | Why |
| --- | --- |
| `intel-media-va-driver-non-free` | Intel's `iHD` VAAPI driver |
| `intel-media-va-driver` | The free fallback `iHD` build, in case non-free packages are blocked |
| `libvpl2` | The oneVPL runtime QSV needs. Without it, `h264_qsv` still lists in `ffmpeg -encoders` and every encode fails on the first frame — indistinguishable from no GPU at all |
| `mesa-va-drivers` | AMD's `radeonsi` VAAPI driver |
| `vainfo` | Makes `docker exec <container> vainfo` a real diagnostic instead of a guess |

## Wiring up a device in Compose

`docker-compose.yml` has **commented-out** device-passthrough stanzas on
both `hub` and `worker`. Nothing about the existing hardening changed to add
them: `ports`, `NEXUSSLATE_BIND`, `NEXUSSLATE_TRUSTED_READ_NETWORKS`, the
read-only media binds, and the Worker's read-only rootfs/tmpfs are all
exactly as before.

### Intel / AMD

```yaml
devices:
  - /dev/dri:/dev/dri
group_add:
  - "104"   # replace with the GID from: stat -c %g /dev/dri/renderD128
```

Both containers run as the fixed unprivileged uid 10001, so `devices:` alone
is not enough — the render node is group-owned by a host-specific GID
(`render` on most distros, `video` on some), and that GID cannot be
hardcoded because it differs per host. Find it with
`stat -c %g /dev/dri/renderD128` and put it in `group_add`.

### NVIDIA

```yaml
environment:
  NVIDIA_DRIVER_CAPABILITIES: all
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu]
```

**This is the gotcha that costs the most debugging time.** The NVIDIA
Container Toolkit defaults `NVIDIA_DRIVER_CAPABILITIES` to `compute,utility`,
which does **not** inject `libnvidia-encode.so.1`. Without `all` (or
`compute,utility,video` if you want to be narrower), `h264_nvenc` still
lists in `ffmpeg -encoders` inside the container and then fails on the very
first frame — a failure mode that looks exactly like "no GPU here" and gives
no hint that the fix is one environment variable.

Both stanzas need the `gpu` image target, not the default one — the plain
image has no VAAPI userspace installed, so without switching `build.target`
(or `image:`) hardware acceleration silently falls back to software either
way.

## Unraid

Unraid has no native Compose support — Compose Manager is an optional
plugin — so `deploy/unraid/` ships two standalone Community Applications
templates instead of assuming it's installed:

- `deploy/unraid/nexusslate-hub.xml`
- `deploy/unraid/nexusslate-worker.xml`

Full walkthrough: [`deploy/unraid/README.md`](../deploy/unraid/README.md).
Summary of what's different from a generic Linux Docker host:

- **No published image yet.** This project doesn't push to a registry, so
  the templates' `nexusslate:v0.19-gpu` tag has to exist somewhere Unraid's
  Docker can see — the simplest path is `docker build --target gpu -t
  nexusslate:v0.19-gpu .` run directly on the Unraid box, which needs no
  registry at all.
- **The uid mismatch has to be fixed by hand, once.** Unraid creates
  `/mnt/user/appdata/...` owned `root:root` or `nobody:users` (99:100); the
  image runs as a fixed unprivileged uid 10001 with no PUID/PGID entrypoint
  wrapper — that's a deliberate property of this image (see the Dockerfile's
  user-creation comment), not an oversight, so the fix is a one-time
  `chown -R 10001:10001 /mnt/user/appdata/nexusslate-hub` (and the same for
  `nexusslate-worker`) before first start, documented in both templates'
  Overview text and in `deploy/unraid/README.md`. The read-only media bind
  needs no such fix — Unraid share permissions are already world-readable.
- **Device passthrough goes in Extra Parameters, not `Config Type="Device"`.**
  Both templates default `ExtraParams` to `--device=/dev/dri:/dev/dri` —
  the pattern other Unraid GPU-transcode templates (Plex, Jellyfin, Tdarr)
  use, and more reliably supported across Unraid versions than the
  `Config Type="Device"` XML field. A host with no `/dev/dri` (CPU-only, or
  an NVIDIA-only box) needs that line removed before the container will
  start.
- **Enrollment is a one-off `docker run`, not `docker exec`.** The Worker
  container's command is `worker run --config
  /var/lib/nexusslate-worker/worker.json`; that file only exists after
  enrollment, and a container that has never had a valid config exits too
  fast to `docker exec` into. `deploy/unraid/README.md` gives the exact
  one-off `docker run … worker enroll …` command — equivalent to what
  `docker compose run --rm worker worker enroll ...` does when Compose is
  available — to run once, before starting the persistent Worker container.

## Driver version: which Alder Lake-N chips bookworm covers

The `gpu` target installs whatever bookworm carries. Verified by building
the layer: `intel-media-va-driver-non-free` 23.1.1+ds1-1,
`intel-media-va-driver` 23.1.1+dfsg1-1, `libvpl2` 2023.1.1-1,
`mesa-va-drivers` 22.3.6-1+deb12u2, `vainfo` 2.12.0+ds1-1 — all five
install cleanly, none fall through to the skip branch.

Alder Lake-N is not one device. The distinction decides whether bookworm is
enough:

| Chip | PCI ID | Minimum media-driver | bookworm's 23.1.1 |
|---|---|---|---|
| N100 | 46D3 | 22.1.1 | sufficient |
| N150 (Twin Lake) | 46D4 | 25.1 | too old |

So a stock `gpu` image is expected to drive an N100 and is expected *not* to
drive an N150. On an N150 — or any Intel part newer than bookworm's driver —
`h264_vaapi` lists in `ffmpeg -encoders` and every encode fails, which is
the same shape as having no GPU at all. `nexusslate doctor` tells the two
apart: an unusable-driver backend reports `runtime=true openable=true
verified=false` with a remedy naming the package, where an absent GPU
reports `runtime=false`.

The escape hatch is backports, applied to a running container or as an extra
build step rather than baked into the target, because it is only correct for
the newer silicon:

```sh
apt-get install --no-install-recommends --yes -t bookworm-backports intel-media-va-driver-non-free
```

Measured on an N100 **against its host driver, not yet inside this image**:
`h264_vaapi` encodes at 13.4x realtime; `h264_qsv`/`hevc_qsv` do **not**
run — the `libmfx-gen` oneVPL backend on ADL-N ships no H.264/HEVC encoder,
so every rate-control mode reports unsupported — while `mjpeg_qsv` and QSV
*decode* both work. VAAPI, not QSV, is the accelerator that works on this
class of hardware, which is why the probe in `internal/media/hardware.go`
verifies each backend by encoding a frame instead of trusting the encoder
list. Confirming the same result inside the `gpu` image is still outstanding.

## Checking it actually worked

Listing an encoder is not the same as it running — a missing runtime
library, a permission problem on the device node, or a driver too old for
the silicon all list fine in `ffmpeg -encoders` and fail on the first frame.
Inside either container:

```sh
docker exec <container> nexusslate doctor      # or `nexusslate worker doctor` on a Worker
```

`doctor` reports what the hardware detector actually selected, with
per-backend remedy output when a backend is present but not working — see
the command's own output for specifics, since that detail is still evolving
independently of this document. `vainfo` (present only in the `gpu` image
variant) is a lower-level check of the same thing:

```sh
docker exec <container> vainfo
```
