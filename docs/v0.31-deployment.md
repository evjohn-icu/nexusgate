# v0.31 部署指南

本文描述 v0.31.0-alpha 的第一次部署。它把素材库能力提供层（转录稿端点、MCP、
ASR 语音搜索）与完整的设计轮 UI 一起交付。**首选 Docker 单 Hub**——多阶段
Dockerfile 在镜像内编译，本地不需要 Go 工具链或 FFmpeg；想要二进制可走
`scripts/build-release.sh`。

> 能力面盘点、Agent 契约 v0.15 与跨机 MCP 细节见
> [v0.31 素材能力提供层](v0.31-footage-capability-provider.md)。
> 更深的 Docker/Unraid/GPU 细节见 [v0.14 部署](v0.14-deployment.md) 与
> [v0.19 GPU Docker/Unraid](v0.19-gpu-docker-unraid.md)。

## 前置

1. **素材目录**：放素材的**父目录**（例如 `/mnt/footage`，或 Unraid 的
   `/mnt/remotes`），而不是某个具体共享。容器以只读 bind 挂载它，`rslave`
   传播让之后挂载的共享无需重建容器即可出现。
2. **Provider key**：处理素材前需要为「视频理解 + ASR」各配至少一个可用的
   provider。`config.example.json` 的示例块把 StepFun、Qwen、Gemini 标为
   `enabled: true`，所以复制它后必须先提供对应 key；不要把示例直接当成无 key
   的默认配置。没有 `config.json` 时，`config.Load` 的内置默认会把这些块设为
   disabled，Hub 可以先启动，但扫描/跑管线前仍要完成 Provider 配置。配置有两条
   互相独立的边界（见第二步）：env/config 旧路由，或浏览器 `/providers` 通道。
3. **Docker**（`docker compose` v2）。

## 第一步：起 Hub（Docker）

> **首次启动前必须先处理 admin-auth。** Hub 跑在容器里时，容器守卫
> `ValidateContainerAdminAuth` 对「默认 `admin_auth=trusted_network` 且没有
> 显式 `admin_auth_networks`」直接拒绝启动（fail-closed，见
> `internal/config/config.go`）。当前 `docker-compose.yml` **没有**透传任何
> admin-auth 配置，所以干净的 `timingdex-data` 卷上直接
> `docker compose up -d --build hub` 会启动即退（容器反复重启），这是安全
> 守卫的预期行为，不是偶发故障。两种合法的解法：
>
> **推荐：`admin_auth: required`（所有管理/写路由都要管理员 token）。** 在
> `docker-compose.yml` 同目录放一个 `docker-compose.override.yml`（Compose
> 自动合并，不改产品文件）：
>
> ```yaml
> services:
>   hub:
>     environment:
>       TIMINGDEX_HUB_ADMIN_AUTH: required
> ```
>
> 然后照常 `docker compose up -d --build hub`。验证：浏览器打开
> `https://127.0.0.1:8787` 会先要管理员登录（输入 `admin-token`）；
> `curl -ks -o /dev/null -w '%{http_code}' https://127.0.0.1:8787/api/v1/roots`
> 不带 token 应返回 `401`（`/api/v1/roots` 是 admin 路由）；`docker compose
> logs hub` 里不再有 admin-auth 拒绝。
>
> **备选：`trusted_network` + 显式 CIDR。** 此时必须写数据卷里
> `config.json` 的 `hub_security.admin_auth_networks`（没有对应环境变量），
> 并且要理解 Docker NAT：端口发布后 Hub 看到的对端一律是网桥网关（一个
> RFC1918 地址），所以列出的网段最终会覆盖整个 Docker 网桥，等于「信任网桥里
> 能碰到端口的任何人」。只有清楚这点才用它。不要靠把守卫设成 `off` 或把端口
> 直接暴露到公网来绕过。

```bash
cd timingdex
export TIMINGDEX_MEDIA_ROOT=/mnt/footage        # 素材父目录
docker compose up -d --build hub                 # 先按上面配好 admin-auth
```

- 首次构建 + 启动；数据落在 `timingdex-data` volume。
- 首次启动生成自签证书 + `admin-token`/`agent-token`，日志打印 **Hub 证书指纹**
  （`Hub HTTPS fingerprint: …`），跨机 Worker 与 MCP 钉扎用。
- 默认绑 `127.0.0.1:8787` → 浏览器本机访问 `https://127.0.0.1:8787`。首次
  访问自签证书时浏览器要「继续前往」一次；本机开发用 curl 加 `-k`
  （`curl -k https://127.0.0.1:8787/…`）——`-k` **只**用于本地自签开发，不要
  在跨机/生产场景用裸 `-k` 关掉校验。
- 跨机访问（浏览器/API/MCP/Worker）不要用裸 HTTP：要么把自签证书/CA 装进
  客户端信任库，要么用 Hub 证书指纹钉扎（见第四步与跨机 Worker）。MCP/Worker
  客户端对非 loopback 的裸 HTTP 会直接拒绝。
- `TIMINGDEX_TLS_MODE=off` 关闭 Hub 自己的 TLS，但浏览器管理员会话在应用层就
  要求 HTTPS（会话按 `r.TLS` 判定，cookie 带 `Secure`），所以 `off` 下浏览器
  登录/管理界面不可用，只适合纯本机 API/CLI 开发。不要照搬「反代终止 TLS、
  明文回源」的部署：该模式本版本未验证，明文回源会被上面的 HTTPS 检查拒掉。
- Key 不要进 shell 历史：放 untracked `.env` 文件（Compose 自动读），
  `GEMINI_API_KEY=…`、`ARK_API_KEY=…` 等已由 `docker-compose.yml` 透传。

## 第二步：配置 Provider

env/config（旧路由）与 `/providers` 通道是**两条互不替换的配置边界**，不要
互相误认：前者写在 `config.json`/环境变量里、由 CLI 启动期校验；后者
存在 Hub 数据库里、经 `/providers` 页面管理、密钥进加密库。运行时每个
capability 优先走 `/providers` 通道（有启用且密钥就绪的成员时），否则回落
旧路由。

- **方式 A（env / `.env`，旧路由）**：`GEMINI_API_KEY=…`、`ARK_API_KEY=…`
  等，重启 Hub 生效。**`ValidateProviderConfig` 在 CLI 的 command switch
  之前运行**：选中 `asr_primary`/`vision_primary`/`repurpose_primary` 且对应
  块 `enabled: true` 而 key 未解析时，`serve`、`pipeline run`、`doctor`、
  `root`、`cache` 和 `search` 等非 Worker 命令都会先退出。因此复制一个
  启用了 Provider 的配置示例前，先放好对应 key；否则连 `doctor` 也无法输出
  诊断。默认配置的 Provider 块是 disabled，所以全新无 config 的 Hub 不需要 key。
- **方式 B（浏览器 `/providers` 通道）**：新增通道，capability 选
  `video_analysis` / `asr` / `repurpose` 等，API Key 经管理员 HTTPS 请求写入
  Hub 加密密钥库，页面不回显。通道不经过上述 legacy config 校验，但在运行期
  解析；能力/模型/endpoint 配错会在第一单失败，而不是拒绝启动。

**浏览器向导限制（当前行为）**：`/providers` 的 beginner wizard 不是通用
Provider 编辑器。它默认同时选择视频理解和 embedding，但视频 Provider 不能
代替 embedding Provider；Gemini 和部分原生 ASR endpoint 不提供 wizard 所需的
模型列表，需改用 Advanced 编辑器手填模型。无鉴权的本地 VLM 也需用
`config.json` 的 `providers.local_vlm` 配置，因为 wizard 当前要求 key。

## 第三步：加素材根 → 扫描 → 跑管线

1. 浏览器 `/library-roots` 添加素材根——**路径填 `/media/library`**（容器内
   路径，不是宿主路径）。
2. 扫描自动入队：`probe → derive → transcribe → [align] → analyze → index`。
   一次显式扫描（浏览器 `/library-roots` 或 CLI `timingdex root scan`）完成后
   会自动触发一次管线运行（`StartPipeline`/`TryRunPipeline`），把当前可租用的
   队列排空；受限作业会留到下一次 run，不需要手动点 run 才能处理普通队列。
3. `/progress` 看进度；跑完后 `/library` 出镜头时间轴、语义/语音搜索与转录稿。

`/setup` 的 Status 是首次引导启发式，不是完整的搜索 readiness 证明：它统计
root、provider channel 和 asset 行，不代表资产已经 probe/analyze/index，也不
会把 legacy `providers.*` env/config 路由计入 Provider 数。完成扫描后仍以
`/progress` 的作业状态和 `/` 是否出现镜头时间轴为准；ExifTool 是可选的，
缺少它只会减少 capture metadata。

> `align` 是可选阶段。没有对齐时，v0.31 的语音搜索直接用 ASR 分段时间，默认
> 管线即可按"说过什么"精确到镜头。

## 第四步：验证能力面

- 转录稿三路径：`GET /api/v1/assets/{id}/transcript`——
  `source=aligned`（带 `words`）/ `source=asr`（无 `words`）/ 无转录稿 → `404`。
- MCP：从 volume 读 `agent-token`，配 `timingdex-mcp`。**默认用 HTTPS + 指纹**，
  不要用裸 HTTP 当 API/MCP 示例：

```bash
go build -o /usr/local/bin/timingdex-mcp ./cmd/timingdex-mcp
export TIMINGDEX_BASE_URL=https://127.0.0.1:8787
export TIMINGDEX_HUB_FINGERPRINT=<指纹>   # Hub 启动日志的 `Hub HTTPS fingerprint: …` 那串
export TIMINGDEX_AGENT_TOKEN=$(cat <data-volume>/agent-token)
```

  `https://` 必须设 `TIMINGDEX_HUB_FINGERPRINT`（缺指纹启动即退）；`http://`
  只对 loopback/link-local 放行，指向其他主机会被拒绝（防止明文送 token）。
  跨机时用 `https://<hub>:8787` + 指纹，见能力提供层文档。

- **MCP 是只读工具集**：`inspect_library`/`search_shots`/`get_timeline`/
  `get_transcript`/`get_asset`/`get_shot`，不创建/修订计划。草稿 draft/revise
  走 HTTP agent-token 工作流（见 `skills/timingdex`），批准与导出由人类管理员
  在浏览器完成。

## 二进制路径（不用 Docker）

```bash
scripts/build-release.sh                  # 出 dist/timingdex + dist/timingdex-mcp
./dist/timingdex serve                    # 或 deploy/systemd/timingdex-hub.service
```

`root add` 填宿主真实路径；其余步骤同 Docker。

## 跨机 Worker（后续）

1. 浏览器 `/workers` → 添加 Worker → `/worker-setup` 向导，或容器 enroll：
   ```bash
   docker compose --profile worker run --rm worker worker enroll \
     --hub https://<hub-ip>:8787 --fingerprint <指纹> \
     --pairing <一次性Token> --name linux-worker-01 \
     --mount <root-id>=/media/library \
     --config /var/lib/timingdex-worker/worker.json
   docker compose --profile worker up -d worker
   ```
   `--config` 必须显式写成 `/var/lib/timingdex-worker/worker.json`：Worker 的
   默认 config 路径是 `~/.timingdex/worker.json`（**不是**数据目录），而 compose
   的 worker 服务把 `timingdex-worker-cache` 卷挂在 `/var/lib/timingdex-worker`、
   运行命令是 `worker run --config /var/lib/timingdex-worker/worker.json`。
   enroll 与 run 用同一个路径，`worker.json` 才会落在持久卷里（重建容器不丢）。
2. 或用二进制 `timingdex worker enroll --config …` +
   `deploy/systemd/timingdex-worker.service`。

**`/worker-setup` 向导的当前限制**（自签 Hub 下不要当「复制即用」）：

- 生成脚本第一步是从 `https://<hub>/api/v1/hub/worker-binaries/<platform>`
  下载 Worker 二进制——只有 `<DataDir>/worker-binaries/` 里预置了对应平台的
  二进制（向导页面会标 available/unavailable）才会成功，否则 404。
- 下载用 `curl -fsSL` / PowerShell `Invoke-WebRequest`，对默认自签证书不会
  自动信任，会在**下载阶段**报证书错误；且脚本生成的 enroll 命令**不带
  `--fingerprint`**，而 `worker enroll` 强制要求 SHA-256 指纹（`--hub` 也必须是
  `https://`）。所以默认自签 Hub 下脚本两处都会卡住。可靠做法是手动
  `worker enroll --hub https://… --fingerprint <指纹> --pairing …`。
- `timingdex worker doctor --config …` 只打印 Hub URL/平台/名称 + 本机硬件
  报告，不连 Hub、不验证租约/连接性：加速是否生效看它，连接问题看 `worker run`
  日志与 Hub 的 `/workers` 页面。

## 关键坑

- **容器路径**：Docker 里 `root add` 必须填 `/media/library`（容器内可见路径），
  不是宿主路径。
- **NAT 与可信网络**：发布端口后，Hub 看到的对端地址是 Docker 网桥网关（RFC1918，
  默认被可信网络守卫信任）。把 `TIMINGDEX_BIND` 暴露到 LAN 前，要么收紧
  `TIMINGDEX_TRUSTED_READ_NETWORKS` 让读路由强制带 token，要么保持 loopback。
- **GPU**：普通镜像内硬件加速回退到软件 x264；`docker build --target gpu`
  出 Intel/AMD VAAPI 镜像，NVIDIA 由宿主 Container Toolkit 提供
  （`NVIDIA_DRIVER_CAPABILITIES: all`）。
- **浏览器管理会话要求 HTTPS**：`TIMINGDEX_TLS_MODE=off` 下 Hub 自己只出明文，
  应用层（会话按 `r.TLS` 判定）与 `Secure` cookie 都会拒掉管理员会话，所以
  `off` 只适合纯本机 API/CLI 开发；「反代终止 TLS、后端明文回源」的模式本版本
  未验证，别照搬。
- **Provider 启用但 key 未设置 → 非 Worker CLI 命令先退出**（v0.31 起
  fail-fast）：旧 env/config 路由中，选中 `asr_primary`/`vision_primary`/
  `repurpose_primary` 且对应块 `enabled: true` 时，`ValidateProviderConfig`
  在 command switch 前运行，`serve`、`pipeline run`、`doctor`、`root`、`cache`
  和 `search` 都会先报缺 key。`/providers` 通道是另一条边界，在运行期解析。
  选中但块未 `enabled` 不算错（默认配置就是推荐 provider + 未启用）。
- **重启孤儿在途租约**：杀进程重启后，上一次进程的在途作业（`running`）由
  executor 注册表（`pipeline_executors`）识别为孤儿，`HealOnStartup` 立即回收；
  无需再等 30 分钟租约过期。前提是新进程先注册自己（serve/pipeline run 已自动做）。
- **SSH 里重启用 `pkill -x timingdex`**：`pkill -f "bin/timingdex serve"` 会匹配
  到 ssh 远端 shell 自己的命令行，把会话一起杀掉。
- **`/tmp` 满（tmpfs）**：小内存机器 `/tmp` 可能是几 GB 的 tmpfs，装素材就满。
  用 `source_staging.mode=none`（直接读源），别指望 NAS→本地暂存。
- **`source_staging.mode=copy` 只对非 probe 作业生效**：probe（`JobProbe`）始终
  直接读原始路径，不落暂存缓存（`sourcePathForJob`）；`copy`/`stage` 只影响
  需要解码/转码整段素材的 derive/transcribe/analyze 等作业。所以 probe 阶段的
  网络/NAS 延迟绕不开。
- **空/未挂载的素材根会被扫成"空库"**：容器内路径若在启动时不存在或没挂上，
  Docker 会把它建成空目录，扫描"干干净净什么都没有"，看起来像坏库而不是配置
  没设。远程共享的机器先确认宿主机侧目录已挂载、再启动容器。
- **`rslave` 只在 Linux 生效**：Docker Desktop（macOS/Windows）不支持 bind
  propagation，会静默忽略 `rslave`，容器启动后宿主侧新挂的共享在容器里看不到。
- **扫描扩展名是白名单，其余静默跳过**：当前支持
  `.mov/.mp4/.m4v/.mxf/.braw/.r3d/.ari/.crm/.dng/.nev/.insv`，其他扩展名
  直接跳过、不入队，也不会报错。ExifTool 是可选依赖（补相机元数据），没有它
  照样扫描，只是 capture 元数据留空。
- **升级前备份数据卷**：先停旧 Hub，再备份整个 `TIMINGDEX_DATA_DIR`（SQLite
  数据库连同 `-wal`/`-shm` 伴生文件一起拷），记录当前 `schema_migrations`
  快照以便回滚；用新版本启动让内置迁移按序应用，跑 `timingdex doctor` 确认
  integrity 后再恢复 Worker/管线。
- **provider key 走环境变量**：`api_key_env` 从进程环境取 key，别写进
  config.json（`api_key` 字段也行但会落盘）。上线后 key 会出现在进程 environ。
- **管线手动 run 会排空队列**：`POST /api/v1/pipeline/run`（及 CLI
  `timingdex pipeline run`、一次显式 root scan 后的自动触发）走 `RunUntilIdle`，
  持续处理到当时可租用队列为空才停——不是"跑一轮就停"。受限作业（尺寸/冷却/
  读速率上限）会推迟到下次 run。
- **`library_supervisor` 是持续扫描/无人值守选项，不是手动 run 的前提**：
  默认 `enabled=false`，开启后每 15 分钟扫描全部 root 并排空队列一次（轮询，
  适合 SMB/NFS 共享）。手动 run 不需要它，两者共用同一单跑守卫，不会叠加并发。
