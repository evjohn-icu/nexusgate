# NexusGate v0.14 deployment

v0.14 separates the authoritative Hub from media-processing workers:

| Role | Owns | Must not do |
| --- | --- | --- |
| Hub | the only SQLite database, migrations, queue state, API, and UI | expose the database to a worker or write source media |
| Worker | temporary processing state, FFmpeg/ExifTool work, and a revocable worker credential | open the Hub SQLite file or write original media |

Every Hub and Worker must see the same source library, but **not** at the same
absolute path. The Hub stores `root_id + relative_path`; each Worker declares
its own read-only `--mount root-id=/local/path` mapping. The Hub data directory
is writable by the Hub only; it is never a shared volume.

## Docker image

`Dockerfile` is a multi-stage build. The first stage compiles the Go binary for
the requested target architecture. The Debian runtime stage includes
`ffmpeg`, `ffprobe`, and `exiftool` (`libimage-exiftool-perl`), runs as the
unprivileged `nexusgate` user, and stores Hub state under `/var/lib/nexusgate`.

Build for the local architecture:

```sh
docker build -t nexusgate:v0.18 .
```

Build an ARM64 image from another architecture with BuildKit:

```sh
docker buildx build --platform linux/arm64 -t nexusgate:v0.18-arm64 --load .
```

The binary uses the pure-Go SQLite driver, but FFmpeg codec and hardware
support still come from the target runtime image and host. ARM workers should
be treated as CPU workers unless their FFmpeg build and device permissions have
been verified.

## Docker Compose

The Compose file defines `hub` and `worker`. `NEXUSGATE_MEDIA_ROOT` is required
rather than defaulted, because a defaulted path would be created as an empty
directory and scan cleanly against nothing — which looks like a broken library
instead of unset configuration:

```sh
export NEXUSGATE_MEDIA_ROOT=/path/to/footage
```

The Hub volume `nexusgate-data` is the only place where SQLite lives. The
worker gets a separate `nexusgate-worker-cache` volume and never mounts
`nexusgate-data`.

`worker` sits behind a Compose profile and is not started by `docker compose
up`. Its `worker.json` only exists after enrollment against a live Hub, so
starting it first just restarts a container that exits immediately.

The Hub publishes `127.0.0.1:8787` only. That is enough for a browser on the
Docker host and avoids an exposure specific to container networking: a published
port puts Docker's NAT in the path, so the peer address the read guard sees is
the bridge gateway — itself an RFC1918 address the guard trusts. Widening the
binding with `NEXUSGATE_BIND` therefore grants anonymous library reads to
anything that can reach the port, however far away it is. Widen it only
together with a `NEXUSGATE_TRUSTED_READ_NETWORKS` range that no peer can match,
which drops reads back to requiring a token:

```sh
export NEXUSGATE_BIND=0.0.0.0
export NEXUSGATE_TRUSTED_READ_NETWORKS=10.99.99.0/24
```

Setting that variable to `0.0.0.0/0` does the opposite — it trusts every caller.
The mutating routes stay behind the administrator token regardless. An HTTPS
reverse proxy in front of the Hub is still the better answer for real LAN
access, and it needs the same treatment: every request arrives from the proxy,
so the proxy has to do the filtering.

Start the Hub:

```sh
docker compose build hub
docker compose up -d hub
docker compose run --rm hub doctor
```

Register and scan the mounted library inside the container so the recorded
path is the read-only container path:

```sh
docker compose run --rm hub root add /media/library
docker compose run --rm hub root list
docker compose run --rm hub root scan <root-id>
```

To use a worker, enroll it with a one-time pairing token issued by the Hub.
Open `/workers` — on the Docker host that is `https://127.0.0.1:8787/workers`,
otherwise through the reverse proxy — read the Hub's local `admin-token` file as
the Hub service account, paste it into the page for that one browser session,
and select **生成配对 Token**. Enrollment writes only the revocable Worker token
and Hub fingerprint into the Worker cache; it never writes Provider keys:

```sh
# Shell-only enrollment placeholders; NexusGate does not read these variables.
export NEXUSGATE_HUB_URL=https://hub:8787
export NEXUSGATE_WORKER_NAME=compose-worker
umask 077
# Use the one-time pairing token displayed by the authenticated /workers page.
docker compose --profile worker run --rm worker worker enroll \
  --hub https://hub:8787 --fingerprint <hub-fingerprint> \
  --pairing <one-time-token> --name compose-worker \
  --mount <root-id>=/media/library --config /var/lib/nexusgate-worker/worker.json
docker compose --profile worker up -d worker
```

Do not put a provider API key in the worker environment. The worker token is
revocable and is stored only in its exact-mode-0600 `worker.json`; the file is
replaced atomically and an unsafe or symlinked config is rejected rather than
repaired. Rotate/revoke the token
after enrollment or suspected compromise. The Compose Worker has no default
Hub URL or credential environment because enrollment writes the pinned HTTPS
connection details into that local config.

For HTTPS, set both certificate paths and mount the directory containing them:

```sh
export NEXUSGATE_TLS_DIR=/etc/nexusgate/tls
export NEXUSGATE_TLS_CERT_FILE=/run/nexusgate/tls/fullchain.pem
export NEXUSGATE_TLS_KEY_FILE=/run/nexusgate/tls/privkey.pem
# Shell-only enrollment placeholder; pass the value to worker enroll --hub.
export NEXUSGATE_HUB_URL=https://hub:8787
docker compose --profile worker up -d hub worker
```

The private key is read-only mounted into the Hub. Do not mount it into a
worker; install only the issuing CA or server certificate in the worker trust
store when the Hub uses a private CA. The Worker must use the HTTPS URL and
certificate fingerprint captured during enrollment, including inside Compose.

## HTTPS configuration

The v0.14 Hub defaults to `NEXUSGATE_TLS_MODE=auto`, which creates and reuses a
self-signed ECDSA certificate under the Hub data directory and prints its
fingerprint at startup. Set `NEXUSGATE_TLS_MODE=files` to use both variables
below, or `off` only behind a separately managed HTTPS reverse proxy:

| Variable | Meaning |
| --- | --- |
| `NEXUSGATE_TLS_CERT_FILE` | PEM certificate or certificate chain presented by the Hub |
| `NEXUSGATE_TLS_KEY_FILE` | PEM private key matching the certificate |

In `files` mode set both or neither. A missing pair is a configuration error;
do not silently fall back to HTTP when the service is meant to be public. Keep the key owned by
the service account with mode `0600`. `NEXUSGATE_LISTEN_ADDRESS` controls the
bind address, for example `127.0.0.1:8787` for a local reverse proxy or
`0.0.0.0:8787` for a firewalled container network.

The Worker CLI stores its Hub URL, pinned certificate fingerprint, revocable
node token, mount mappings and cache path in its mode-0600 config file. Use an
`https://` URL and install the private CA in the Worker OS trust store for
production; do not disable certificate verification to make pairing convenient.

Provider keys remain Hub configuration. As of v0.16 the default remains
**deny**, but an operator may enable `allow_worker_provider_credentials` for a
paired, trusted Worker. The key is not persisted on the Worker; it is returned
only for a compatible operation while that Worker owns a task lease. This is a
delivery/audit limit, not upstream-key revocation—use Hub JSON proxy mode when
the Worker must never see a Provider key. The proxy deliberately rejects media
payloads, so it cannot turn the NAS Hub into a video relay.

## Generic Linux systemd installation

Logging is text to stderr by default; set `NEXUSGATE_LOG_FORMAT=json` for
structured JSON (journald-friendly) and `NEXUSGATE_LOG_LEVEL` to
`debug`|`info`|`warn`|`error` to tune verbosity. Invalid values fall back to
the default (`text`/`info`) with a warning.

These units assume a package-style Linux installation. Adjust the binary path
and the media path once, then keep the same absolute media path on every
worker.

1. Install the v0.14 binary at `/usr/local/bin/nexusgate`. Native installs
   also need `ffmpeg`, `ffprobe`, and `exiftool` available on `PATH`; the
   supplied container image already includes them.

2. Create the service account and directories:

   ```sh
   sudo useradd --system --home /var/lib/nexusgate --shell /usr/sbin/nologin nexusgate
   sudo install -d -o nexusgate -g nexusgate -m 0700 /var/lib/nexusgate
   sudo install -d -o nexusgate -g nexusgate -m 0700 /var/lib/nexusgate-worker
   sudo install -d -o nexusgate -g nexusgate -m 0750 /srv/nexusgate/media
   sudo install -d -o root -g nexusgate -m 0750 /etc/nexusgate/tls
   sudo install -d -o root -g nexusgate -m 0750 /etc/nexusgate
   ```

   Copy or mount original media below `/srv/nexusgate/media`. Grant the
   `nexusgate` account read/execute access only; do not grant write access.

3. Install the units and create the Hub environment file:

   ```sh
   sudo install -m 0644 deploy/systemd/nexusgate-hub.service /etc/systemd/system/
   sudo install -m 0644 deploy/systemd/nexusgate-worker.service /etc/systemd/system/
   sudo install -o root -g nexusgate -m 0640 /dev/null /etc/nexusgate/nexusgate.env
   sudo tee /etc/nexusgate/nexusgate.env >/dev/null <<'EOF'
   NEXUSGATE_DATA_DIR=/var/lib/nexusgate
   NEXUSGATE_LISTEN_ADDRESS=127.0.0.1:8787
   NEXUSGATE_TLS_CERT_FILE=/etc/nexusgate/tls/fullchain.pem
   NEXUSGATE_TLS_KEY_FILE=/etc/nexusgate/tls/privkey.pem
   NEXUSGATE_TLS_MODE=files
   EOF
   sudo chmod 0640 /etc/nexusgate/nexusgate.env
   ```

   Keep direct HTTPS for browser administration. `NEXUSGATE_TLS_MODE=off` is only
   a controlled HTTP compatibility mode for non-browser clients; the Hub does not
   trust forwarded headers, so an unconfigured TLS-termination proxy does not make
   browser Sessions valid. For direct HTTPS, install the certificate and key under
   `/etc/nexusgate/tls` and keep the key mode `0600`.

4. Add the library using the exact path visible to the Hub and start it:

   ```sh
   sudo -u nexusgate NEXUSGATE_DATA_DIR=/var/lib/nexusgate \
     /usr/local/bin/nexusgate root add /srv/nexusgate/media
   sudo systemctl daemon-reload
   sudo systemctl enable --now nexusgate-hub.service
   sudo systemctl status nexusgate-hub.service
   ```

5. Configure a worker separately. Redeem a fresh, short-lived Hub pairing
   token once; it creates a mode-0600 Worker config containing the revocable
   node token and its local root mapping, but never a Provider key:

   ```sh
   sudo -u nexusgate /usr/local/bin/nexusgate worker enroll \
     --hub https://hub.example.internal:8787 --fingerprint <hub-fingerprint> \
     --pairing <one-time-token> --name linux-worker-01 \
     --mount <root-id>=/srv/nexusgate/media \
     --config /var/lib/nexusgate-worker/worker.json
   sudo systemctl enable --now nexusgate-worker.service
   ```

   Treat the generated config as a deploy-time secret: do not check it into the
   unit, repository, or image. Revoke and replace it at the Hub when a worker
   is retired or handed off. Provider API keys never belong in this file.

The Hub unit uses `ProtectSystem=strict` and treats `/srv/nexusgate/media` as
read-only. The worker unit has its own state directory and the same media path;
it cannot access the Hub's state directory or database.

## Windows worker service

Windows workers can run the same `nexusgate.exe worker` command. Install
matching v0.14 binaries and tools first:

1. Put `nexusgate.exe`, `ffmpeg.exe`, `ffprobe.exe`, and `exiftool.exe` in
   controlled directories. Add the tool directory to the service account's
   `PATH`, or use the installer that supplies those tools.
2. Create a dedicated local account such as `NexusGateWorker` and grant it
   `Read & Execute` on the media directory only. Do not grant `Modify` or
   `Write` to the original footage tree.
3. Create `C:\ProgramData\NexusGate\worker` for scratch state and keep the
   Hub database on the Hub host. Set the worker's `NEXUSGATE_DATA_DIR` to the
   worker directory, never to a network share containing `nexusgate.db`.
4. Use a service wrapper such as WinSW or NSSM. With WinSW, place a wrapper
   beside the binary as `NexusGateWorker.exe` and use this minimal XML as
   `NexusGateWorker.xml`:

   ```xml
   <service>
     <id>NexusGateWorker</id>
     <name>NexusGate Worker</name>
     <description>NexusGate v0.14 media worker</description>
     <executable>C:\Program Files\NexusGate\nexusgate.exe</executable>
     <arguments>worker run --config C:\ProgramData\NexusGate\worker\worker.json</arguments>
     <workingdirectory>C:\ProgramData\NexusGate\worker</workingdirectory>
     <env name="NEXUSGATE_DATA_DIR" value="C:\ProgramData\NexusGate\worker" />
     <onfailure action="restart" delay="10 sec" />
   </service>
   ```

   Install and start it from an elevated PowerShell prompt with the wrapper's
   `install` and `start` commands. Store the token file with an ACL readable
   only by `NexusGateWorker`, and rotate/revoke it after pairing or a host
   handoff. Do not put provider API keys in this XML.

Before installing the service, run `nexusgate.exe worker enroll` once using
`--mount <root-id>=D:\\NAS\\Footage` and the Hub certificate fingerprint. The
Windows Worker may use a different local path from the Hub.
If the worker is processing originals directly, make the directory available
to the service account as read-only. A Windows Hub can use the same wrapper
with `serve`, but the SQLite rules do not change: only one Hub owns the file.

## Linux ARM worker notes

- Prefer a native `linux/arm64` build or the matching multi-platform image;
  do not run an amd64 image through emulation for sustained media work.
- Verify `ffmpeg -version`, `ffprobe -version`, and `exiftool -ver` on the
  worker before enrollment. Codec availability differs between distributions.
- Software fallback is the safe default. `/dev/dri` or vendor-specific
  accelerators should be added only after testing the host permissions and
  the selected FFmpeg profile.
- Give the worker its own local scratch/cache volume and mount footage
  read-only. Never mount the Hub data volume, its SQLite WAL/SHM files, or a
  backup directory into an ARM worker.
- Keep the media path stable across Hub and workers. When the Hub schedules a
  job against `/srv/nexusgate/media`, an ARM worker needs that same path or a
  declared v0.14 path mapping.

## Backup and safety checklist

- Stop the Hub before copying its SQLite data directory, or use a SQLite-aware
  backup. Include the `-wal` and `-shm` files when they exist; never back up a
  live file by copying only `nexusgate.db`.
- Do not run migrations, `root` commands, or SQLite maintenance from a
  worker. The Hub is the only database owner.
- Keep source media mounts read-only in Docker, systemd, and Windows ACLs.
  Derived media and cache outputs belong under the writable Hub/worker state
  directories.
- Pairing tokens are single-use and short-lived, and only a Hub administrator
  token can create one. Worker tokens are revocable; keep them out of logs and
  source control. Direct Provider credential delivery is opt-in only for a
  trusted paired Worker; its lease expiry cannot revoke an already-delivered
  upstream key. Prefer the Hub JSON proxy if that exposure is unacceptable.
- If a worker is lost, revoke it at the Hub, remove its token, and rotate any
  credential lease that may still be active. Re-pair only after the worker
  host and its read-only media boundary have been checked.
