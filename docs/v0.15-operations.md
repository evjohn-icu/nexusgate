# NexusGate v0.15 operations guide

This guide describes the delivered v0.15 behaviour. It separates capabilities
that are covered by automated tests from items that still need validation on
your own NAS and Worker hardware.

## Product boundary

NexusGate is a local-first **Video Asset Intelligence Layer**:

```text
original footage
  → understand
  → organise
  → discover
  → reuse in an editing workflow
```

It is not an NLE replacement or an automatic video generator. The library page
answers “what usable shots do I already have?”; the Repurpose workspace answers
“which existing shots can support this brief?” The final edit remains human
work in Resolve, Premiere, Final Cut, or another editor.

## Normal operating flow

1. Run the NAS Hub with a dedicated data directory. The Hub is the sole owner
   of SQLite, workflow state, derived media and Provider secrets.
2. Add a library root that is read-only to NexusGate. The Hub scans and probes
   source material in place; it never writes a proxy, sidecar or edited media
   beside an original.
3. Configure Provider channels at `/providers`. Add an independent channel for
   each capability and desired fallback order. One channel may contain several
   keys for the same Provider.
4. Run the processing workflow. Local mode may derive media itself; a Worker
   may derive media from a mounted NAS root and upload its artifacts to Hub
   storage.
5. Review the library. Filters cover date, region, camera and shoot session.
   A session selector shows a human-readable title/date/camera/region label but
   searches using the stable session identifier.

## Provider channels

Provider channels are capability-isolated. A video request cannot select an
ASR key, and an embedding request cannot select a Curator key.

| Capability | Supported channel providers |
| --- | --- |
| Video analysis | Gemini, Qwen Video, Volcengine Video, local VLM |
| ASR | StepFun, Qwen ASR, Volcengine ASR |
| Embedding | OpenAI-compatible, Gemini, Volcengine Agent Plan, Volcengine Coding Plan |
| Tag curation | OpenAI-compatible, Volcengine Agent Plan, Volcengine Coding Plan |
| Repurpose planning | OpenAI-compatible chat |

Within an unchanged channel route, the Hub keeps Provider-pool state in memory:
bounded concurrency, member rotation, retryable failure cooldown and ordered
fallback. A change to channel metadata or configured-key readiness replaces
only that capability’s route atomically.

Existing environment/config-file Provider settings remain the fallback when no
enabled, compatible channel exists. If neither is configured, optional
features preserve their prior deterministic/heuristic behaviour where one
exists; video analysis and ASR remain visibly unconfigured rather than
inventing output.

### Secret handling

The admin page sends a key only to the authenticated Hub request. The Hub
stores it encrypted at rest under:

```text
$NEXUSGATE_DATA_DIR/provider-secrets/     mode 0700
└── provider-secrets.enc                  mode 0600
```

SQLite contains only a secret reference. Browser storage, normal API listings,
logs, Worker configuration and task events must not contain a Provider key.
The channel runtime resolves a key only in Hub memory while making the Provider
request and redacts it from returned error/raw-response paths.

## NAS Hub and Workers

The Hub handles control-plane work: scanning, source probe, key management,
database writes, validation, indexing and UI. A Worker handles disposable
execution-plane work: local source staging, FFmpeg, hardware encode/decode and
artifact upload. Workers use `root_id + relative_path` and map the root to
their own SMB/NFS/local mount; they do not open the Hub SQLite database.

Worker pairing uses a single-use token and a Hub certificate fingerprint.
Treat a Worker as a trusted machine, but do not put an upstream Provider key on
it: v0.15 deliberately rejects Worker credential delivery. A delivery TTL
cannot revoke a third-party key after a Worker has received it. Future remote
Provider execution needs a Hub proxy or a Provider-issued revocable token.

### Hardware expectations

- Windows x64 and Linux x64 are the preferred high-throughput proxy Workers.
- Linux ARM64, including RK3566/RK3568-style systems, is valid as a slow,
  single-task 720p H.264 Worker. It must self-report the actual FFmpeg/hardware
  capabilities; NexusGate does not assume `rkmpp` exists.
- The Hub itself can stay lightweight. Proxy/transcoding is the dominant CPU or
  GPU workload; scanning, indexing and most API calls are comparatively light.

## Capture memory and colour

NexusGate records vendor-neutral camera identity, capture time, source colour,
RAW classification and evidence. It recognises common Blackmagic, DJI, Sony,
Canon, Apple, GoPro, Insta360, Panasonic, Nikon, Fujifilm, RED and ARRI
families.

Automatic shoot sessions are conservative: captures must share a root and
camera identity and fall within a 30-minute gap, unless a reel/session marker
provides stronger evidence. Original media and metadata are never altered.

Exact capture coordinates are private. Normal asset/session responses expose a
region label only. The source-precision location endpoint is Hub-admin
protected and should be used only when genuinely needed.

| Source type | v0.15 handling |
| --- | --- |
| SDR | Standard preview/proxy pipeline |
| HLG / PQ | HDR → SDR Rec.709 preview route |
| Apple Log / recognised Log | LUT-aware SDR preview route; missing LUT is explicit |
| BRAW/R3D/CRM/ARI/N-RAW/ProRes RAW | Reliable classification and explicit renderer status; no fictional proxy promise |

Visual analysis, thumbnails and timeline frames should consume the correctly
rendered SDR derivative, never an unrendered Log/RAW original. NLE handoff
continues to reference the original file and its original colour metadata.

## Acceptance checklist

Automated checks completed for the v0.15 source package:

- Complete Go test suite and static analysis.
- Provider-channel retries, key redaction, legacy fallback, capability
  isolation, session browse privacy, capture persistence and CJK search.
- Linux x64, Linux ARM64 and Windows x64 binary builds.

Run these before treating a deployment as production-ready:

1. Process one representative clip on a Windows GPU Worker.
2. Process one representative clip on a Linux x64 Worker.
3. Process one 720p proxy on the intended ARM Worker; slow completion is
   acceptable, silent corruption is not.
4. Verify NAS mount mapping, Worker reconnect and Hub restart recovery.
5. Verify one HDR clip, one Apple Log clip with its intended LUT, and one
   proprietary RAW clip reaches the correct visible state.
6. Confirm a Provider key appears neither in `nexusgate.db`, Worker config nor
   Hub logs after a failed request.

## Known limits and next work

- Proprietary RAW decoding/rendering is a pluggable future renderer, not a
  v0.15 guarantee.
- Provider management currently creates and lists routes; edit/disable/delete,
  explicit connection tests and operational charts are the next UI increment.
- Scheduling matches declared capabilities. It does not yet predict duration,
  preempt tasks, wake remote machines or optimise cost.
- Real-machine smoke testing is still required for each NAS/FFmpeg/driver
  combination.
- The next product layer is stronger asset intelligence: visual vector search,
  similar-shot retrieval, rare-asset discovery and higher-quality repurpose
  proposals.
