# v0.21 — 无人值守巡检、额度耗尽的等待，与时间线导出

这一版补上素材库两端的最后一段人工操作：**进来**的时候不用手动 `root scan` + `pipeline run`，
**出去**的时候不用手抄时间码进剪辑软件。中间夹一件运维上的事：套餐额度用完时，
队列该怎么等。

## 无人值守巡检

`timingdex serve` 现在可以自己按时重扫所有素材目录，然后把队列排空。默认**关闭**——
升级一个既有安装不应该让它突然开始自己干活、自己花钱。

```json
{ "library_supervisor": { "enabled": true, "scan_interval_minutes": 15 } }
```

### 为什么是轮询，不是 fsnotify

目标部署把素材放在 SMB/NFS 共享上。在那里 inotify 要么根本收不到别的主机做的改动，
要么直接不可用；而 Docker 的媒体 bind 用 `rslave` 传播（见 v0.20），
共享可以在 Hub 运行期间从 bind 底下出现和消失。

一个漏掉事件的 watcher 是**静默失败**：素材就是永远没被索引，而且没有任何东西会说这件事。
定时器漏不掉任何东西——最坏情况只是发现晚了一个间隔。这个取舍在这类部署里不是接近的。

间隔小于一分钟会被抬到一分钟。一次扫描要走完整棵目录树，`0` 或 `1` 被读成「尽可能快」
会让网络共享永远处于忙碌状态，而换不来任何东西。

### 这个循环刻意写得很笨

一个 goroutine，一次一趟，趟的主体**内联执行**而不是自己再起一个 goroutine。
于是「扫描不能叠加」和「Hub 停的时候管线趟也要停」这两条是**形状本身的性质**，
而不是某个锁的正确性。

- 定时器在一趟还没跑完时触发，那一下**被丢弃而不是排队**。`time.Ticker` 的 channel
  只存一个值，趟又跑在同一个 goroutine 上，所以比间隔还慢的扫描既不会自我重叠，
  也不会攒出一堆补偿趟。
- 管线趟走 `Service.TryRunPipeline` 而不是 `StartPipeline`。后者把 goroutine
  分离到 `context.Background()` 上——那是它的设计，但那意味着服务已经停止提供服务之后，
  它还会继续发付费的 Provider 请求。`serve` 现在在返回前等巡检循环真正结束
  (`stopSupervisor(); <-supervisorDone`)，这个等待只有在没有分离 goroutine 时才是有意义的。
- `TryRunPipeline` 和 `/progress` 上的「运行待处理任务」按钮共用同一把单趟锁。
  操作者手点的运行和巡检不可能同时压同一块盘：谁先到谁继续，另一个报 busy。

### 静默时段管的是整趟，不只是扫描

时段窗口（v0.18）是操作者对「这台机器什么时候可以动素材库」的表态，而无人值守循环
正是为这句话写的那个场景。所以窗口关闭时**整趟都不做**：走一遍 NAS 目录树本身就是负载，
而在这里启动管线趟会在被要求的时段之外开始付费分析。

人手触发的东西一律不受这个门限制——`/progress` 的按钮和 CLI 说跑就跑。
`RunUntilIdle` 内部的逐作业旋钮（体积推迟、作业间冷却、读取速率上限）也完全没动。
这里没有加第二层限速，只是决定那一趟**发不发生**。

`/progress` 会显示巡检状态：是否在跑、上一趟的结果、下一趟的时间。
其中 `held_off_peak` 和 `held_until` 单独存在的理由是：没有它们的话，
一个完全按配置正常工作的巡检，和一个已经悄悄死掉的巡检，长得一模一样。

## 额度耗尽：等，而不是失败

推荐部署跑在有硬性月额度的套餐上（见 v0.15 的 Provider 通道）。额度用完时，
通道里**每一把 key 一起**答 429。这是关于账户的事实，不是关于这个作业的事实。

所以当一条能力路由上所有成员都失败时，`providerchannels` 返回 `ErrRouteExhausted`，
管线把作业**按墙上时钟推迟五小时**，并把这次租约消耗掉的尝试次数**还回去**。

换成重试会在十秒内烧掉这个作业的全部尝试预算，然后因为一次停机把它永久判死；
而那几次尝试每一次都是付费调用。

`/progress` 上这些作业显示为「等待额度」，并有一个「立即重试等待额度的作业」按钮
（`POST /api/v1/pipeline/resume-deferred`）供额度提前恢复时手动放行。
页面上显示的是 Hub 自己定义的常量 `provider_route_exhausted`，
而不是上游返回的文本——后者可能内嵌被截断的响应体，那个留在管理员 token 后面。

## 导出：EDL 与 FCPXML

批准过的翻新方案可以导出成剪辑软件能读的东西：

```text
GET /api/v1/repurpose/plans/{id}/export.edl      # CMX3600
GET /api/v1/repurpose/plans/{id}/export.fcpxml   # FCPXML 1.9
```

`/repurpose` 页面在方案批准之后才出现这两个按钮。段落顺序和镜头选择就是人批准的那一份，
导出时不重新排序、不重新选片。

### 为什么两条都是管理员专属，而且不进 agent allowlist

- FCPXML 内嵌**每一个原始文件的绝对路径**——这正是 `access_original_media_paths`
  拒绝的东西。这是它不需要重新链接就能导入的原因，也是它必须留在管理员这边的原因。
- EDL 不带路径，但它是**有人会拿去剪**的成品。导出是选择从「提案」变成「一次剪辑」的那一刻，
  所以它跟锁定方案的那次人工批准共用同一道门。

`GET /api/v1/agent/capabilities` 的 `denied_actions` 现在声明 `export_timeline`，
`skills/timingdex/references/api-contract.md` 说同一件事。
两处必须一致：代码里够不着但契约里没写的路由，Skill 每一轮都还是会去试。

未批准的方案返回 **409**，不是文档。选中的镜头落在管线还没探测过的素材上返回 **422**，
并**按文件名**指出是哪个文件——不给路径，因为同一段文本会进日志，而日志没有管理员门。

### reel 命名

优先用摄影机元数据里的 reel 而不是文件名：那是这段素材开拍时的编号，
也是剪辑助理拿来对的那个编号。文件名是兜底。

两卷素材带同一个 reel 编号是很平常的事（两张卡都叫 A001）。这种撞名在进 `nleexport`
**之前**就被消解掉了——它自己的防撞逻辑只对不同的输入字符串生效，
在这一层撞掉的名字它完全看不见，结果会是一个镜头被静默链接到另一个文件上。

## 升级：这次升级对已有库做了什么

从这个版本开始运行 Hub，启动时会自动改写数据库里已经存过的每一条时间戳。这一步不用手动
做任何事，也不需要操作者选择要不要执行——它是这次升级自带的一次性动作。

migration `0021_v021_sortable_timestamps.sql` 覆盖 81 条 `UPDATE` 语句、跨 47 张表，把每一张表
里已经存过的时间戳从可变宽度重写成固定 30 个字符的宽度。它跟其余每一个 migration 一样，在
`Migrate` 方法里被包进一个事务里跑：这份 SQL 要么整体生效，要么在出错时整体回滚，不会出现
"改了一半"的库（`internal/repository/sqlite/repository.go` 第 207–221 行）。它只会在升级后的
第一次启动时跑一次——`schema_migrations` 表记着哪些 migration 已经跑过，跑过的不会再跑第二遍
（同文件第 193–203 行）。

它修的问题是什么：这个库里所有时间戳字段之前用 Go 的 `time.RFC3339Nano` 格式写入，这个格式
会把小数点后面的末尾零去掉——`.512300000Z` 写出来是 `.5123Z`。而这些时间戳在 SQL 里是按
**字符串**比较谁先谁后，不是按真正的时间值比较。字符串比较下 `.5123Z` 比 `.51234Z` **大**，
因为字符 `Z` 排在字符 `4` 后面——尽管 `.51234` 这个时刻其实更晚。这会让"按创建时间取最新一条"
"判断一个租约是否已经过期"这类查询，在极少数情况下给出错误答案，而且不会报错——查询照常返回
结果，只是顺序或判断偶尔是错的。

migration 之后，写入用的是一个固定 30 字符的新格式（`sortableTimeLayout`，
`internal/repository/sqlite/repository.go` 第 533 行；写入函数 `formatTime` 在第 535 行），
同一个值不管小数部分末尾有没有零，输出宽度都一样，字符串比较和时间先后从此重新一致。这份
migration 本身是幂等的：一个值只要长度已经是 30 个字符，就被判定为"已经是新格式"而跳过，重复
跑这份 SQL 不会把已经转换过的行再转一遍（migration 文件开头的注释，第 1–8 行；每条 `UPDATE`
语句末尾的 `length(...) <> 30` 判断，例如第 10–17 行那一条）。

没有改动任何读取时间的代码：`time.RFC3339Nano` 仍然能把新格式的固定宽度字符串解析回同一个
时间点，所以这次修复只需要一个新常量加一份改写脚本，不用碰任何 `time.Parse` 调用点。

这份 migration 在一个大库上要跑多久，仓库里没有现成的测量数据，这里不编一个数字出来。
