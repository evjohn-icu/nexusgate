# v0.33 · 免口令状态的界面设计（补 v0.33 计划书任务 5）

原计划书的「任务 5 · 界面」只写了行为（藏输入框、显示文案），没写视觉。
实现按那个写法做出来了，但结果不成立。这份是补的视觉规格。

## 现状问题

真二进制 + 默认 `trusted_network` 下截图（不是 fixture，fixture 见文末）：

侧栏底部出现一行**孤零零的橙色文字「本机免口令」**，上面是一大片空白
（原来登录按钮占的位置），下面才是状态读数。

四个问题：

1. **它不像一个状态，像一句没来得及删的报错。** 没有容器、没有圆点、没有和任何
   既有词汇对齐，就是一行浮着的橙字。而侧栏下方**已经有**一套系统状态的表达方式
   （圆点 + 标签 + 右对齐值），免口令显然属于同一类信息，却另起了一种画法。
2. **上方留下一块空白**，读起来像"这里本该有东西但没加载出来"。
3. **文案把范围说小了。**「本机免口令」听起来是"只有这台机器"，但
   `trusted_network` 的真实规则是"可信网段内的任何设备"——在 NAS 上跑的时候，
   室友的笔记本、访客手机、IoT 设备都在这个范围里。这个差别是实质性的，
   文案不该淡化它。
4. **只在侧栏说了一次。** 真正有后果的地方（`/providers` 写密钥、`/workers` 发配对令牌）
   什么都没有。

## 设计

### 一、免口令是系统状态，用系统状态的画法

不要独立文案块。**在状态读数里加第五行**，和 Hub / 处理 / 模型 / 节点并列：

```
● HUB      正常
● 处理     空闲
○ 模型     未配置
● 节点     0 在线
● 访问     内网免口令      ← 新增
```

- 标签用 `.status-cell .k` 的既有样式，文案 `访问`
- 值按模式：
  | `admin_auth` | 值文案 | 圆点 |
  |---|---|---|
  | `required` | `需口令` | `.dot.ok` |
  | `trusted_network` | `内网免口令` | `.dot.warn` |
  | `off` | `完全开放` | `.dot.err` |
- `href` 指向 `/settings`；`title` 写全范围，例如
  `可信网段内的任何设备都可以进行管理写入（改这条：hub_security.admin_auth）`
- **`required` 那一行也要显示**。只在放宽时才出现的提示，等于把"安全"变成沉默、
  "不安全"变成噪音；两种状态都可见，才是一个读数而不是一个警报。

这样做的好处：复用既有组件、宽度对齐、永不换行，也不会在侧栏留空洞。

### 二、口令区在放宽模式下整块收起

`required` 之外，`.shell-auth` 整块 `hidden`（输入框、登录、退出、状态文字一起），
不要只藏输入框留下一行文字。`margin-top:auto` 的间距由状态读数顶上，空白自然消失。

### 三、有后果的页面各说一次，只说一次

`/providers` 页顶部（「已配置的模型」面板之上）加一条 callout：

```html
<div class="callout callout--attention">
  <span>这台 Hub 当前对内网免口令：可信网段里的任何设备都能读写这里的模型配置。
  要改成必须输入口令，把 hub_security.admin_auth 设为 "required"。</span>
</div>
```

`/workers` 页同理，文案换成配对令牌的后果。

**只加这两页。** 每页都挂一条就成了背景噪音，第三天起没人再看见它。
选这两页的理由是它们的写入后果最具体：一个把密钥写进加密库，一个发放能加入集群的令牌。

`off` 模式下这两条 callout 升级成 `callout--contradicted`，文案改成
「口令已关闭：任何能访问这个端口的人都是管理员。」

### 四、文案

- 不要用「本机」——真实范围是网段，不是这台机器。
- 不要用「已登录 / 未登录」——放宽模式下这两个词都不成立，说的是"不需要登录"。
- `off` 用「完全开放」而不是「口令已关闭」：前者说的是后果，后者说的是设置。
  界面上应该说后果。

## 实现约束

- 状态第五行走 `shellHeaderHTML()` 里现有的 `cells` 循环，加一个
  `{"status-access", "访问权限", "访问"}` 条目；`id` 和 `class="dot"` 的既有约定不要破坏。
- 值由 `shellScriptBlock` 里已有的 `applyAdminAuthMode()` 填，用现成的
  `statusCell('status-access', state, text)`，不要新写一套 DOM 操作。
- `/api/v1/setup/status` 已经返回 `admin_auth`，不需要新端点。
- `app_shell_sidebar_test.go` 的状态格断言要同步加一行，其余断言不动。

## 一并要修的：这条 UI 路径现在没有任何测试覆盖

> **订正（2026-08-30）**：本节原来的成因诊断是错的，而它开的药方已经落地却没有
> 治好病。原文写 fixture 拿到的是零值 `""`、规范化只在 `Load()` 里，因此
> "把规范化挪到取用点，fixture 保持不动即可自动跟上默认值"。实际上：
> `HubSecurityConfig.AdminAuthMode()` 已经存在（`internal/config/config.go:227`），
> `Service.AdminAuth()` 也已经改走它（`internal/app/service.go:570`）——**药方吃完了**；
> 但 `browserfixture/fixture.go:54` 把 `AdminAuth: "required"` **显式写死**，
> 不是零值，所以它不会跟上任何默认值，覆盖洞原封不动地留着。
> 下面保留原文以存档，正确的诊断与修法见本节末尾。

`internal/api/browserfixture/fixture.go` 直接构造
`config.Config{HubSecurity: config.HubSecurityConfig{AdminToken: ...}}`，
**不经过 `config.Load()`**，所以 `AdminAuth` 是零值 `""`。

而"空值 → `trusted_network`"的规范化**只写在 `Load()` 里**，于是：

- 浏览器 fixture 跑的是 `required`，而所有真实部署默认是 `trusted_network`
- **免口令这条界面路径不被任何测试或截图覆盖**——正是这次新增的功能
- 任何直接构造 `config.Config` 的代码（测试、嵌入者）都会静默拿到 `required`，
  和文档写的默认值不一致

实测对照：

| | `admin_auth` | 无凭据 `GET /api/v1/roots` |
|---|---|---|
| fixture（不走 Load） | 字段缺失 | 401 |
| 真二进制（走 Load） | `trusted_network` | 200 |

**修法**：把规范化从 `Load()` 挪到取用点，让零值和文档默认值处处一致。
例如给 `HubSecurityConfig` 加 `AdminAuthMode() string`（`""` → `"trusted_network"`），
`Service.AdminAuth()` 和 API 层的 `adminAuth` 都改成走它。
`Load()` 里那段规范化可以保留（提前失败仍然有价值），但不再是唯一的一处。

然后 fixture 保持不动即可——它会自动跟上默认值，浏览器冒烟也就覆盖到免口令路径了。
如果希望冒烟同时覆盖两种模式，给 fixture 加一个环境变量开关，默认跑默认值。

### 订正后的诊断与修法

规范化那一层**已经修好了**，可以从待办里划掉：`AdminAuthMode()` 在
`internal/config/config.go:227`，`Service.AdminAuth()` 在
`internal/app/service.go:570` 走的就是它，直接构造 `config.Config` 的代码不再
静默拿到 `required`。

覆盖洞之所以还在，是另一个原因：

```go
// internal/api/browserfixture/fixture.go:54
config.HubSecurityConfig{AdminToken: AdminToken, AdminAuth: "required"}
```

**fixture 显式钉死了 `required`。** 它不是零值，所以规范化改到哪里都影响不到它；
"fixture 保持不动即可自动跟上默认值"这句预测因此不成立。

当时给出的修法是：**给 fixture 加环境变量开关**（例如
`TIMINGDEX_FIXTURE_ADMIN_AUTH`），并让浏览器冒烟跑两遍。

### 已修（2026-08-30）：覆盖洞用另一条路补上了

最后没有走"跑两遍"那条路，因为它要动 fixture、动 CI 的启动段，还要把一次冒烟
变成两次；而这条 UI 分支的**唯一**输入是 `GET /api/v1/setup/status` 的
`admin_auth` 字段（`app_shell.go` 的 `adminAuthMode` 只从这一处读）。所以冒烟
改成在浏览器里拦截这一个响应、只改这一个字段：

```ts
// testdata/browser-smoke/specs/smoke.spec.ts
await page.route('**/api/v1/setup/status', async (route) => {
  const response = await route.fetch();
  const body = await response.json();
  body.admin_auth = mode;               // 'trusted_network' | 'off'
  await route.fulfill({ response, json: body });
});
```

三条用例（`trusted_network` / `off` / `required` 作回归底线）各跑 desktop 与
mobile 两个 project，断言第 5 个 Access 状态格的文字与 dot 状态、`.shell-auth`
的 `hidden` 属性、以及 `/providers` 与 `/workers` 上 `#admin-auth-callout` 的
可见性、类名（`--attention` vs `--contradicted`）和文案。

**边界要说清楚**：这补的是**界面分支**的浏览器覆盖，不是服务端是否真的豁免凭据——
后者是另一个断言，由 `TestAdminAuthModeRootWriteGuard` 钉住，两者不可互相冒充。
fixture 仍然显式跑 `required`，`browserfixture/fixture.go` 未改。
