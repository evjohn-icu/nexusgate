# v0.21 — 检索与搜索

素材库现在能按类型、景别、运镜、音频类型、质量、可用场景六个维度筛选，不再只能按
日期、地区、相机这些拍摄信息缩小范围。这份文档讲这六个维度从哪来、哪些接口认它们、
网页上现在能做到什么程度、以及搜索排序今天诚实的样子。

## 六个维度都是老字段，只是接上了查询接口

这六个维度来自 `internal/normalize` 包里的受控词表：素材类型、运镜、景别、音频类型、
质量、可用场景（`normalize.go` 第 23–28 行）。模型分析结果落库前就已经被收窄成词表里的
固定值（`ValidateAndNormalize`），这一版没有新增任何字段——这些值一直存在，只是查询接口
以前够不到它们。

它们只在素材这一级存在：`asset_analysis` 表一行对应一个素材，没有单独的"镜头景别"这种列。
用镜头搜索接口按景别筛时，实际取的是这个镜头所属那条素材的景别，不是逐镜头判断出来的
（`internal/domain/asset_browse.go` 第 39–50 行的 `FacetFilter` 文档注释写明了这一点）。

时长不是这样。素材层面的"最短/最长时长"指整条素材自己的长度，用 `media_metadata.duration_ms`
比较（`internal/repository/sqlite/asset_browse.go` 第 118–129 行）；镜头搜索里同名的参数指的是
那个镜头自己的起止跨度，用 `end_ms-start_ms` 比较（同文件第 137–147 行）。这是故意的两种含义，
不会被统一成一种（`internal/domain/asset_browse.go` 第 39–50 行同一段注释）。

## 哪些接口认这些筛选，筛错了会怎样

素材列表、两个搜索接口、以及"找相似镜头"接口都接受这六个维度加时长范围：

- `GET /api/v1/assets`（素材列表，`internal/api/server.go` 第 132 行）
- `GET /api/v1/search`（全文/标签搜索，第 163 行）
- `GET /api/v1/search/shots`（镜头搜索，第 164 行）
- `GET /api/v1/search/shots/hybrid`（镜头混合搜索，第 165 行）
- `GET /api/v1/shots/{id}/similar`（找相似镜头，第 166 行）

合法值统一来自 `normalize` 包，一个参数名对一份词表列表，写在一处供五个接口共用
（`facetQueryFields`，`internal/api/server.go` 第 857–870 行）。同一个参数用逗号隔开可以传多个
值，取"或"——比如 `shot_size=wide,medium` 命中远景或中景任意一种；不同参数之间取"且"。

传一个词表里没有的值——比如把 `wide` 打成 `wdie`——接口直接报 400，错误信息里点名是哪个参数、
哪个值（`internal/api/server.go` 第 905–907 行）。这不是可有可无的校验：一个库里根本没有素材的
查询，和一个拼错了筛选条件的查询，返回的都是空列表，两者长得一模一样。库里明明有素材却因为
打错一个字就被当成"没有"，比报错更糟。

## 网页上，每个维度目前只能选一个值

`/library` 页面新增了六个下拉框和两个时长输入框，但要说清楚一件事：每个下拉框现在只能选
一个值。接口本身接受逗号分隔的多值 OR（上一节说的那样），但页面发出的请求每个参数只带一个值
——下拉框本身就是单选控件（`facetSelectHTML`，`internal/api/library_page_v015.go` 第 185–193
行），组装查询串的 JS 也是逐个下拉框取它的 `.value`（同文件第 121 行）。想同时看"远景或中景"，
今天做不到，只能分两次筛选、各看一遍结果。这是网页这一版还没做多选控件，不是接口的限制。

时长按秒输入，页面转换成毫秒再发给接口，留空表示不限（`internal/api/library_page_v015.go`
第 179–180 行）。

## 处理状态统计条不再和卡片列表打架

打开"景别=近景"这类筛选后，页面顶部的处理状态统计（多少条可用、多少条排队中……）现在会跟着
变，而不是继续显示筛选前的总数——以前这两块各算各的，统计条完全不理会筛选条件。

统计接口 `/api/v1/library/processing-summary` 和卡片列表接口现在从同一份查询条件出发：承载六个
维度的 `FacetFilter` 被内嵌进两者共用的过滤器结构（`domain.AssetCollectionFilter`，
`internal/domain/collections.go` 第 30–38 行），再由同一个转换函数变成实际查询用的过滤条件
（`collectionToAssetCardFilter`，`internal/repository/sqlite/collections.go` 第 16–26 行）。统计
SQL 为此新增了一个 `asset_analysis` 的 LEFT JOIN，不能写成 INNER JOIN：素材刚扫描完、还没跑
分析的时候，几乎所有素材都没有 `asset_analysis` 行，INNER JOIN 会把它们全部丢掉，统计条会在
"没加任何筛选"的情况下也显示成接近零（`internal/repository/sqlite/collections.go` 第 131–143
行）。

保存的"视图"也用同一条路径：以前保存的视图筛选条件只在算统计时生效，点开视图看卡片列表时这些
条件却被丢掉了；现在两处走的是同一个转换函数，不会再各算各的（`ListAssetCardsInCollection`，
`internal/repository/sqlite/collections.go` 第 114–129 行）。

## 搜索：`limit` 数的是筛选后真正命中的数量

举个例子：库里有五万个素材，搜"海边"并加上"景别=远景"的筛选，`limit` 设成 20。以前的做法是
先按"海边"取够 20 条命中，再看这 20 条里有没有远景——库大的时候，这 20 条命中里可能一条远景
都没有，页面就会显示"没有结果"，即便库里其实有不少远景的海边素材，只是没排进那没经过筛选的
前 20 条里。

现在 facet 条件被折进了每一条候选 SQL 自己的关联子查询里，`limit` 数的是"筛选之后真正命中的
行数"，不是先取够 `limit` 条候选再从里面挑（`internal/repository/sqlite/repository.go` 第
1690–1703 行的注释；具体做法是给每条查询加一个 `EXISTS` 关联子查询，`facetExistsGuard`）。

这不等于"返回库里所有匹配项"：它保证的是返回的这 `limit` 条以内条条都是真正匹配的，如果匹配
总数超过 `limit`，超出的部分依然不会出现——跟以前一样，只是现在"在 `limit` 以内"这句话终于是
真的，而不是"在没被筛选之前的候选窗口以内"。

不加任何 facet 时，实际发出的 SQL 跟这次改动之前一个字节都不差，原有的查询计划不受影响
（`internal/repository/sqlite/repository.go` 第 1825–1828 行的注释）。

## `GET /api/v1/assets?ids=`：按 id 精确取，超过上限直接报错

搜索命中一批素材 id 之后，现在可以直接拿这批 id 去要卡片数据，不用再套一层"先取前 300 条，
再从里面挑出命中的那几个"的旧逻辑。

`ids` 参数最多接受 200 个 id，超过这个数直接 400，不会悄悄截断到 200 个再返回
（`maxListedAssetIDs`，`internal/api/server.go` 第 1223 行；截断判断在第 1244–1246 行）。截断比
报错更危险：调用方以为拿到了全部结果，实际上少了几条，而且没有任何信号提示它少了。

`ids` 留空或不传，语义是"不限制"，不是"什么都不匹配"。这条要记住，因为它有一个反直觉的后果：
一次搜索如果一条都没命中，调用方**不能**拿着空列表去调这个接口——那样等于没传 `ids`，
返回的会是整个库。正确的做法是命中为空时干脆不发这个请求，页面就是这么做的。

## 排序：跟着卡片列表走，不是相关度——这不是差一个参数的事

搜索结果今天不按"哪条更相关"排序，说清楚：这不是一个开关没打开，而是排相关度需要的东西现在
不存在。

命中一批 id 之后，实际渲染顺序由 `GET /api/v1/assets?ids=` 决定，它跟平时浏览素材库用的是同一条
SQL、同一个排序——按拍摄时间倒序，拿不到拍摄时间就退回发现时间倒序
（`internal/repository/sqlite/asset_browse.go` 第 175 行）。这跟"这条结果匹配得好不好"没有关系。

想做相关度排序会撞上一个更底层的问题：`/api/v1/search` 命中一个词走的两条路径给不出同一种分数。
按标签匹配的那条路径只返回 id，不算任何分数（`internal/repository/sqlite/repository.go` 第
1883–1889 行）；按全文匹配的那条路径也没有调用 SQLite 的 `bm25()` 排序函数，同样只返回 id
（第 1900–1922 行）。镜头搜索那边确实用了 `bm25`（`internal/repository/sqlite/repository.go` 第
1412、1417 行），在混合搜索里还把它转换成一个 0 到 1 之间的分数参与排序（第 1504–1519 行），但
那是镜头搜索自己的实现，素材搜索没有对应的东西。要把"相关度"做成一个能排序的数字，需要先让标签
匹配和全文匹配算出同一种可比的分数——这在今天的代码里不存在，也不是加一行 `ORDER BY` 就能补上的。
