# NexusGate v0.20 — NAS mounting: the ladder and why each rung sits where it does

The question this document answers: how does an operator point NexusGate at
footage on a NAS with the least friction, given the Hub normally runs in a
container as a fixed unprivileged uid 10001 (see the Dockerfile's
`useradd --system --uid 10001` and, on Unraid, the chown-once fix in
[GPU Docker images and Unraid deployment](v0.19-gpu-docker-unraid.md))? This
is a decision record, not a tutorial: each rung states what it costs the
operator and why it is, or is not, the default. `internal/mount` (see its
package comment) already implements the host-side half of rung 0 — it prints
mount commands, it never mounts anything itself, because mounting needs root
and surviving a reboot needs a line outside `$NEXUSGATE_DATA_DIR`, the one
place this Hub is allowed to own.

## The ladder

### Rung 0 — the share is already mounted on the host (the default)

Jellyfin, Immich, PhotoPrism, Frigate and Navidrome all take the same
position: the host mounts the share, the container gets a bind mount of an
already-mounted path. This is not laziness. A decoder needs cheap random
access to seek within a multi-gigabyte file, and every userspace/FUSE
alternative — davfs2, sshfs, a Go SMB client behind an `io.Reader` — degrades
seek badly enough that it changes how usable scrubbing and thumbnailing feel.
A kernel-mounted share behaves like a local filesystem to everything above
it; nothing else on this list does.

The remaining friction was that a share mounted *after* the container
started stayed invisible to it — Docker's default bind propagation is
`rprivate`, so a mount event on the host under the bind's source path never
reaches the container's view of that path, and the only fix was recreating
the container. `docker-compose.yml` now sets `bind.propagation: rslave` on
the media bind and binds a *parent* directory — `/mnt/remotes` on Unraid
(where Unassigned Devices mounts SMB/NFS shares), `/mnt` on bare metal —
instead of one specific share, so a share added on the host later shows up
inside the container live, with no `docker compose up -d` needed to pick it
up. `rslave` is one-directional: the container still cannot create or affect
mounts the host would see, so this does not weaken the read-only bind.

On Unraid the same property is set a different way: the Community
Applications templates in `deploy/unraid/` give the media bind
`Mode="ro,slave"`, which is the "Read Only slave" entry Unraid's own Access
Mode control offers — so it survives a WebGUI edit as an ordinary path
field, and does not have to be smuggled through `ExtraParams` the way the
`/dev/dri` device flag is. Propagation earns its place there more than
anywhere else: Unassigned Devices remounts its remote shares when the array
stops and starts, so even a share that *was* present when the container
started goes stale behind a private bind.

Limits worth stating plainly: this is Linux-only, Docker Desktop
(macOS/Windows) does not support bind propagation and silently ignores the
setting rather than erroring, and `rslave` only ever flows host→container.

### Rung 1 — NFS via Docker's built-in `local` volume driver

```yaml
driver_opts:
  type: nfs
  o: "addr=nas.local,ro,soft,nolock"
  device: ":/export"
```

The Docker daemon performs the mount in the host mount namespace itself, so
the container needs no added capability. The decisive property is that
**there is no password in this form at all** — NFS exports are authorised by
client IP, not by credential — so nothing sensitive is ever written to disk
or to `docker volume inspect` output. Enabling an NFS export is a checkbox on
Synology, QNAP, TrueNAS and Unraid alike. This is the recommended
docker-native path.

### Rung 2 — SMB via the same `local` driver: works, with a cost that has to be stated

```yaml
driver_opts:
  type: cifs
  o: "username=...,password=...,ro"
  device: "//nas.local/share"
```

Docker's `local` volume driver forwards `o:` straight to the `mount(2)`
syscall; it never shells out to the `mount.cifs` userspace helper. That
helper is what understands `credentials=/path/to/file` — the syscall path
does not, and rejects it with "invalid argument"
([docker/cli#2802](https://github.com/docker/cli/issues/2802), open since
2020-10-20). The practical consequence is that the password has to go inline
in `o:`, where it lands in cleartext in `docker volume inspect` and in
`/var/lib/docker/volumes/<name>/opts.json` on disk. A related leak — the
same password appearing in the *error message* on a failed mount — was
[moby#43596](https://github.com/moby/moby/issues/43596) and was fixed by
[moby#43597](https://github.com/moby/moby/pull/43597); that half is closed.
The storage exposure is not a bug being tracked for a fix — it is how the
syscall path works — so it remains.

Set that against this project's own secret boundary: provider keys live only
in the encrypted `secretstore` and are never written to SQLite, an API
response, browser storage, or a log line (see Security boundaries in
`CLAUDE.md`). A NAS password sitting in cleartext in Docker's own volume
metadata is a real regression against that standard, which is why rung 2 is
documented as a fallback, not offered as the default.

The host-side alternative avoids the whole problem: `mount -t cifs` run
directly on the host *does* invoke `mount.cifs`, which supports
`credentials=`, so a 0600 file kept outside Docker entirely satisfies the
kernel helper without the password ever reaching a Docker-managed file. That
is exactly what `internal/mount`'s Linux SMB guidance already does (see
`linuxSteps` in `internal/mount/mount.go`) — one more reason rung 0 stays
first for SMB specifically.

### Rung 3 — mounting inside the container: rejected

The two ways to make a container mount a share are `CAP_SYS_ADMIN` or a
bind-mounted `docker.sock`. `CAP_SYS_ADMIN` is real privilege escalation and
meaningful container-escape surface. A bind-mounted `docker.sock` is worse,
not better — it is equivalent to handing the container host root, which
would defeat the entire reason the image runs as uid 10001 instead of root.
Neither is on the table.

### Rung 4 — a userspace SMB client (`go-smb2`, what rclone uses): deferred, not rejected outright

This is possible in principle and is recorded here as deferred, with the
reason, rather than as a to-do. A userspace SMB client gives an `io.Reader`,
not a filesystem path, and FFmpeg needs a path to open and seek within.
Making that work means either staging the whole file first — which
`source_staging.mode: copy` already does for exactly this reason, but a
thumbnail only needs one frame, and pulling a 50 GB source to get it is the
wrong trade for that job — or running a loopback HTTP server in front of the
reader and pointing FFmpeg at it over HTTP Range requests, which is
meaningfully more moving parts for the same result rung 1 already gives for
free. It would also pull in a dependency beyond the stdlib plus the two libraries
this project allows itself (`modernc.org/sqlite`, `nhooyr.io/websocket`; see
CLAUDE.md's Project section). Worth a project of its own; not worth it as a
rung anyone should climb today.

## Protocols evaluated and dropped

| Protocol | Why it's not supported |
| --- | --- |
| **AFP** | Apple deprecated it — no AFP server has shipped in macOS since macOS 11, and Apple's own guidance is to use SMB. The only maintained Linux client, Netatalk Client (a 2024 fork of the previously decade-dormant afpfs-ng), is FUSE-based, so inside a container it costs `/dev/fuse` plus `CAP_SYS_ADMIN` — rung 3's price, paid for a protocol every AFP-capable NAS also serves over SMB. |
| **WebDAV (davfs2) / SSHFS** | Both FUSE, both carry rung 3's privilege cost inside a container, and both have the same weak random-access performance that rules out rung 4 — the one property a video decoder actually needs. |
| **rclone's Docker volume plugin** | Genuinely capable — covers SMB, WebDAV and SFTP — but it is a managed Docker plugin the operator has to install and keep updated separately: a second moving part outside this project's own release process. Worth mentioning to an advanced operator who already runs it for other containers; not adopted as guidance here. |
| **iSCSI** | Block-level rather than file-level: the initiator gets a raw device and puts an ordinary filesystem on it, and an ordinary filesystem cannot be safely mounted by two hosts at once. Sharing a library between the Hub, a Worker and whatever else already reads the NAS is the normal case here, so the wrong shape — a clustered filesystem would fix it and is far more machinery than a read-only media library justifies. |

## What the `/library-roots` wizard actually does

The wizard detects whether the Hub is running containerised and frames the
mount instructions accordingly: containerised, the `mount` commands it
prints are host-side — run on the Docker host, not inside the container,
matching rung 0 above — because a container has no business acquiring
`CAP_SYS_ADMIN` to mount anything itself.

The last step is the exception, and getting it wrong is how this flow used
to dead-end. `nexusgate root add` is executed by the Hub, so on a
containerised Hub it needs the path *inside* the container, not the
host-side mount point every step above it names. The two are different
directories: propagation only carries mounts made under the media bind's
source, so the default mount point moves under that source, and the Hub
reads its own `/proc/self/mountinfo` to learn where the same directory
surfaces in here. Verification stats the translated path for the same
reason — asking `os.Stat` about a host path from inside a container reports
"does not exist" about a namespace this process cannot see, which is
exactly what a correctly-followed flow used to produce. Both paths are
named in the UI rather than one being silently swapped for the other.

That translation is derived, not assumed, and it can fail: field 4 of
`mountinfo` is the mount's root within its *source filesystem*, which is
the host path only when the host mount and that filesystem share a root.
When the bind cannot be determined, or when the operator picks a mount
point outside it, the wizard says so and emits no `root add` command at
all — a command against a guessed path either fails outright or, worse,
succeeds against an empty directory Docker created on demand and registers
a library root that will never hold anything. When the Hub is containerised it also renders a
Compose `driver_opts` stanza for the share the operator actually typed —
one stanza, not a menu, because a `RootInspection` knows only the single
address it was given and cannot invent an NFS export path for a NAS
reachable at an SMB one. Which rung that stanza lands on therefore follows
the input: an NFS address produces the credential-free form (rung 1) with
nothing to warn about, and an SMB address produces the rung 2 form with its
cleartext-in-volume-metadata caveat rendered *above* the YAML — an operator
who has already scrolled past the block to copy it has already pasted the
password — plus a note that re-running the wizard against an NFS export, if
the NAS can serve one, avoids the trade entirely. Rungs 3 and 4 are never
offered, because neither is guidance this project is willing to stand
behind.
