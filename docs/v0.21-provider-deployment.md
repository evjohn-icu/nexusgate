# v0.21 — 模型服务商部署

Hub 的模型调用有一条形状：**Key 只在 Hub 里，管线根本不知道自己在用哪把 Key**。
`/providers` 是唯一输入 Key 的地方，密钥存在加密的 `secretstore` 里，管道各阶段
（probe、ASR、视频理解、Tag 整理、embedding）一律走同一套按能力域调度的通道。这份
文档讲三件事：额度从哪家买、多把 Key 怎么并、按能力怎么分流，以及这些边界为什么在那里。

## 推荐：火山引擎豆包 Agent Plan

入门档 **¥9.9/月**，**硬上限**：当月额度用完即停，**没有超量计费**。推荐它就是
因为这个上限——最坏情况是索引暂停，不是一张意外账单。按量计费的服务商额度是不设防的，
一个异常脚本或一次全库重扫就能烧出账单；套餐把这个风险从「钱」变成「暂停」。

第二个理由是套餐**连 embedding 一起覆盖**：语义检索（embedding 能力）、ASR 和
Tag curation 都吃同一把 Agent Plan 的 Key（`config.go` 里 `volc_agent_plan`、
`volc_agent_plan_embedding`、`volc_asr` 三块的 `APIKeyEnv` 都是
`ARK_AGENT_PLAN_API_KEY`）。想「让检索能搜」不必再养第二家服务商。

### 鉴权是 Bearer，不是 X-Api-Key

Agent Plan 的四个内置块（`volc_agent_plan`、`volc_coding_plan` 以及各自的
`_embedding`）默认就是 `Authorization: Bearer <key>`——`internal/config/config.go`
里四块都写 `AuthHeader: "Authorization"`、`AuthScheme: "Bearer"`，测试
`TestVolcPlanProvidersDefaultToBearerAuth` 把这个钉死了。

`volc_asr`（Seed ASR 2.0）是例外：它是一条独立协议、独立主机的服务，**本来就**用
`X-Api-Key`，别把它跟 plan 块混为一谈（README 明确说了这一点）。

**警告**：这份默认是被修过的。更早的 `config.example.json` 给 plan 块发的是
`"auth_header": "X-Api-Key"` / `"auth_scheme": "raw"`，而 Agent Plan 只认 Bearer，
会回 **401**——还是对你自己的 Key 回 401，看起来像 Key 错了而不是默认值错了，于是
当时的绕法是把它重建成本质一样的 openai_chat/openai_embeddings 通用通道。现在默认
已经修正，但**已存在的 `config.json` 会覆盖修正后的默认**：从旧 `config.example.json`
拷过配置的安装，需要把四个 `volc_*_plan*` 块里那两行删掉（或改成
`Authorization`/`Bearer`）。代码注释（`config.go` 第 60–66 行）和 README 都写的是这条。

## 一条通道，多把 Key

Hub 的通道形状是：**一条通道 = 一个 endpoint / 协议 / 模型**，通道里可以挂**多个
member**，每个 member 有**自己的 Key、权重（weight）、并发上限（max_inflight）**。
这个形状在 `providerchannels/metadata.go` 的 `Channel`/`Member` 上，`/providers` 页面的
「KEY 列表」就是逐 member 填这三样东西。

运行时按 `providerpool` 挑人：**并发最少者优先，打平时游标轮换**（`Select` 里逐个比较
各 member 的 inflight、取最小，并让 cursor 越过选中的位置），权重影响「cursor 从哪个
member 起步」的频率，member 遇到 408/429/5xx/网络错进入 **1s→2s→4s（上限 30s）**的冷却
（`errors.go` 的 `ClassifyFailure`）；401/402/403 不走冷却，见下面「Key 耗尽自动退休」一节。
通道之间**按 route 顺序 fallback**（`executor.go` 的 `Execute` 逐通道试）。并发打满的
member 是**跳过而不是排队**（`pool.go` 的 `eligible`），所以一把被限流的 Key 只是暂时
不出现，不会拖住整条通道。

### 实操：几个账号的 ¥9.9，并到同一条通道

买几个账号的 ¥9.9 套餐，把每把 Key 在**同一条通道**里加成一个 member。额度按账号
独立计，三把 Key 就是**三倍月额度**：一把耗尽只会让那一个 member 退休，另外几把照常
干活，池子自动把负载匀过去（见下面「Key 耗尽自动退休」一节——这条在早期版本里并不
成立，一把耗尽过的 Key 曾经会拖垮整条通道，写这份文档时已经修好）。`max_inflight`
本来就为「几把各自限速的 Key」而存在（`pool.go` 第 33–36 行），每把按 1 起步，让并发在
Key 之间摊开，而不是让一个最快的前端把整条通道打满。

### Key 耗尽自动退休，而不拖垮整条通道

一把 Key 如果回 401（撤销）、402（欠费/额度耗尽）或 403（无权用这个模型），`providerpool`
现在会把这个判断跟「这次调用要不要重试」分开：`ClassifyFailure`（`internal/providerpool/errors.go`）
把 401/402/403 归成单独一类 `MemberSpent`——这三个状态码回答的是「这把 Key 还能不能用」，
不是「这次请求本身有没有问题」——`Pool.complete` 收到这一类失败会把这个 member 直接标记
成不可用（跟手动点掉启用开关的效果一样），而不是像其它失败那样进冷却。下一次 `Select`
自然会跳过它，选中通道里的下一把 Key。退休**不占**每条通道三次重试的预算——扣预算的是
「这次也许换个时机能成」的赌注，一把已经死掉的 Key 再赌一次没有意义，扣了预算只会让它
在后台占位置，拖慢真正该换 Key 的时刻。

**这个退休只在内存里，进程重启或编辑一次通道就会清空**，不写回数据库。原因是从这里的
视角看，一把被撤销的 Key 和被限流一小时的 Key 长得一模一样，只有人能分清是哪种，所以
交给人来处理：改一下通道配置（哪怕不改内容，保存一次也行）或者重启 Hub，这把 Key 就会
再拿到一次证明自己的机会。判断退不退休只看状态码，不看响应体文字——`redactError` 已经
把状态码单独拼回 `*common.StatusError` 保留在错误链里（见上面「通道卫生」一节），一个
转发服务如果把请求原文回显进错误信息，不会因为文字里恰好出现"unauthorized"之类的词就被
误判成 Key 耗尽。

**怎么看到哪把 Key 退休了**：`GET /api/v1/admin/provider-channels/status`（需要 Hub
管理员令牌）返回运行时视图，每个 member 带 `retired` 布尔，每条通道带 `available`。
它跟 `GET /api/v1/admin/provider-channels` 是两件事：后者返回数据库里存的通道配置，
退休不写库，所以在那里永远看不见。

这个接口只报它确实知道的事。运行时状态挂在按能力缓存的 executor 上，而 executor 是
按需构建的——一个能力如果自 Hub 启动（或自上次编辑该通道）以来没有真正路由过一次调用，
就没有 executor，接口对它返回 `has_runtime_data: false`，而不是假装一切正常。**重启之后
所有能力都是这个状态**，这是实话，不是故障：退休本来就只活在内存里。反过来说，
`has_runtime_data: false` 不代表通道有问题，只代表还没人用过它。

页面还没接。`/providers` 今天仍然只显示配置，所以要看退休状态得 curl 上面那个接口，
或者从 `/progress` 观察任务是不是开始走「等待服务商额度」这条路（下一节）。把它画进
页面是后续工作。

### 全部耗尽的形状

`executor.go` 的 `routeFailingEverywhere` 判定「每个 member 上次的结果都还值得以后再试」——
可重试的冷却，或者一把刚刚退休的 Key，都算。花光额度的账号会**对每把 Key 同时回 429 或
401/402/403**，于是下一次调用可能一把请求都不发就判断整条路耗尽（`executor.go` 第
352–372 行的注释）。此时 `Pipeline` 把作业**停 5 小时**（`pipeline.go` 的
`ErrRouteExhausted` 分支，`providerRouteDeferral = 5 * time.Hour`），**这次租约消耗的
尝试次数原样交还**，不算重试；`/progress` 把它标成「等待服务商额度」，右上角有「立即
重试等待额度的作业」按钮，对应 `POST /api/v1/pipeline/resume-deferred`（`service.go` 的
`ResumeDeferredJobs`）——充完值或故障清除后点一下就能提前放出来。

为什么是 5 小时而不是重试：额度是**按月、硬**的，几秒后重试没有意义，而 5 小时一次的
探针几乎不花钱，账号充值或跨月后能自己恢复（`pipeline.go` 第 240–249 行的注释）。
要是把它当普通可重试错误走退避链，空账号会在十秒内烧光作业的整个尝试预算然后被判
永久失败——而那条链上的每一次尝试都是一次**付费**调用。停靠（`DeferJob`）不消耗尝试
次数，所以队列永远不会因为一个空账号永久失败工作。

有一种情形绕过了上面这条「整条路耗尽」的判断：通道里最后一个还没退休的 member 如果正好
被另一个并发请求占满了 `max_inflight`，`Select` 会直接返回「无可用」而不发出请求——这个
member 因此从没被"尝试"过，`routeFailingEverywhere` 就不能把它算作耗尽的一部分（它的
判定要求每个 member 都真的试过）。这时如果这次调用命中的是另一把已经耗尽的 Key，那个
未包装的 `MemberSpent` 错误会原样冒到 `isRetryableJobError`（`internal/app/pipeline.go`）
这一层，而不是先变成 `ErrRouteExhausted`。这里的处理是照样按可重试处理：退休已经在
`Pool.complete` 里发生过了，下一次尝试自然会绕开这把死 Key，选中别的 member。

## 按能力配置

通道是**按能力域隔离**的：一个能力永远选不到另一个能力路由上的 member。
`providerchannels/metadata.go` 里的真实能力常量是：

- `asr` —— 语音转写
- `video_analysis` —— 视频理解
- `alignment` —— 对齐
- `tag_curator` —— Tag 整理
- `embedding` —— 向量检索
- `repurpose` —— 翻新方案

`/providers` 页面新增通道的下拉暴露其中五个（video_analysis、asr、embedding、
tag_curator、repurpose）；`alignment` 走 legacy 的 `external_command`（外部命令），
不在通道页面上。每个能力的内置服务商选项（页面第 56 行）：

- video_analysis：Gemini、千问视频、火山视频、本地 VLM
- asr：StepFun、千问 ASR、火山 ASR
- embedding：OpenAI 兼容 Embeddings、Gemini Embeddings、火山 Agent/Coding Plan Embeddings
- tag_curator：OpenAI 兼容 Chat、火山 Agent/Coding Plan
- repurpose：OpenAI 兼容 Chat

所以理论上每个能力可以指向不同服务商。**但注意：视频理解的选项里没有「Agent Plan」这个
名字**——`videoProvider` 只接受 gemini / qwen_video / volcengine_video / local_vlm 四个
名字（`provider_channel_runtime.go` 第 821–847 行）。但这个 provider 名字只是**适配器
选择器**，决定用哪套 wire 协议和请求形状，不决定端点：`applyProviderChannelConfig`
（`provider_channel_runtime.go` 第 958–983 行）会用通道记录覆盖内置默认的 BaseURL / Path /
Model / AuthHeader / AuthScheme / TimeoutSeconds 和 Key。所以把 provider 选成
`volcengine_video`、endpoint 填套餐端点 `https://ark.cn-beijing.volces.com/api/plan/v3`、
鉴权 `Authorization`/`Bearer`、Key 用 Agent Plan 的 `ARK_AGENT_PLAN_API_KEY`，视频理解
就能走套餐；一条 `video_analysis` 通道挂几把套餐 Key，就是把几把 Agent Plan Key 并起来
做视频理解。不配通道、只启用默认时，内置的 `volcengine_video` 指向按量计费的 Ark
（`/api/v3`、`ARK_API_KEY`，`config.go` 第 219 行），视频理解就走按量账单。

**警告**：本仓库无法确认套餐是否提供视觉模型及其模型名，请以火山的套餐说明为准。

### 首次用户怎么配

一个 ¥9.9 的 Agent Plan 账号，两套配法，看你更怕哪一头。

**额度可控优先（推荐）**：全部走 Agent Plan 的 Key。ASR（火山 ASR）、tag_curator（火山
Agent Plan）、embedding（火山 Agent Plan Embeddings）各一条通道，视频理解再开一条
`video_analysis` 通道：provider 选 `volcengine_video`、endpoint 填套餐端点
`/api/plan/v3`、Bearer 鉴权，把几把套餐 Key 都加进这一个通道当 member。最坏情况是整库
暂停到跨月或再加一把 Key——永远不会来账单。

**视频不挤占套餐**：视频理解单独走按量计费的火山视频（`/api/v3`、`ARK_API_KEY`）或千问
视频（DashScope，`DASHSCOPE_API_KEY`），其余三样仍吃套餐。套餐花完视频照跑，代价是消耗
大头的那份账单没有上限。

我会选**额度可控优先**：视频是消耗大头，把它放进硬上限里最坏只是暂停，而暂停不会亏钱；
把大头留在按量计费上，等于把「异常脚本烧账单」的风险重新搬回来。

（硅基流动这类 OpenAI 兼容的 embedding 服务可以指进「OpenAI 兼容 Embeddings」通道——
这个选项本来就标注为 OpenAI-compatible，端点和模型名自己填即可。但硅基流动不是 Hub
的内置 provider，本文档不替它背书价格或模型。）

## Key 永不离开 Hub

这是上面所有形状的原因，单独说一遍。provider Key 只存在于加密的 `secretstore`：
`provider-secrets/` 目录 **0700**、加密文件 **0600**（`secretstore/store.go` 第 24–32
行），数据密钥是独立的 `store.key`，不从 admin token 派生（否则轮换 token 会锁死整个
库）。Key 不进 SQLite、不进 API 响应、不进浏览器存储（页面里的 Key 只在密码输入框里
活着，写入后即清除、永不回显，`providers_page_v015.go` 顶部三条注释讲的就是这个边界）、
不进 Worker 配置，也不进日志或错误串——`secretstore` 的 `String()`/`MarshalJSON` 只
输出引用数量（`store.go` 第 379–399 行），运行时把每次调用返回里的 Key 从错误和原始
输出里抹掉才落库。

**轮换数据加密密钥**：`nexusslate secrets rekey` 生成新 `store.key`、全量重加密
所有已存密钥，并把旧 key 备份到 `provider-secrets/store.key.pre-rekey`（原子四阶段，
失败时原状恢复；需要 Hub 管理员 token，来源与服务进程相同）。轮换后旧备份可删除；
无 store / 无 token 时报错不 panic。

Worker 默认走 **Hub 的 JSON 代理**：Worker 把请求体发给 Hub，Hub 在服务端解析凭证、
替它发出，再把响应里出现的 Key 替换成 `[REDACTED]` 才返回（`provider_channel_operations.go`
第 416 行）；代理只收 `application/json`、上限 **2 MiB**，媒体和分片直接拒绝。只有当
`hub_security.allow_worker_provider_credentials` 被**显式**打开（默认拒绝，
`service.go` 第 730 行，`IssueWorkerCredential` 里的第一个判断）时，Worker 才会拿到一把
**租约绑定、仅存内存**的凭证——lease 是审计/交付窗口，不是把第三方长期 Key 转发给 Worker。

**这两条 Worker 路径都只读 `providers.*`（legacy 配置），不读 `/providers` 通道**——
哪怕那条通道已启用、member 健康。这是故意的，不是漏做：通道携带的是通道范围的 Key、
member 池和健康状态，这些东西按设计留在 Hub 侧；Worker 的凭证/代理边界本来就比通道路由
窄（见 `IssueWorkerCredential`、`issueProviderCredentialForProxy`，都用
`credentials.NewBroker(s.cfg.Providers, nil)` 构造，从不读
`internal/providerchannels`）。这份文档前面把「优先用 `/providers` 而不是配置文件」当
成推荐路径——如果某个能力只通过通道配置过、`providers.*` 里对应的块仍是空的，Worker
向 Hub 要这个能力的凭证或走代理都会被拒绝，Hub 侧的错误现在会把这种情况和「哪儿都没配」
分开归类（`app.ErrWorkerProviderConfiguredAsChannelOnly` vs
`app.ErrWorkerProviderNotConfigured`），不会再看起来像是通道配置本身出了错。这两种情况
现在也在 HTTP 状态码上分开：Worker 收到的是 **403**（能力确实配了，只是配成了通道，
Worker 凭证/代理这条路按设计不读通道）而不是 **503**（这个能力哪儿都没配过），两条路径
以前不管是哪种原因都统一回 400。要让某个 Worker 能直接拿到某能力的凭证，或者通过代理
调用它，就还要在 `providers.*` 里给那个能力补一块 legacy 配置——哪怕 `/providers` 里
已经有一条通道在正常为管线内部提供同一能力。

## 通道卫生：一个确定的 4xx 不再吃退避链

一次请求如果因为 Key 填错、或者账号根本调不到某个模型而收到一个 4xx，Hub 现在认得出"这个
错误重试也没用"，不会再照着 1s→2s→4s→…→30s 的退避链把同一次付费调用重复打好几次。以前的
行为是：一把填错的 Key，会让每个撞上它的任务白白多花几次付费调用才被判定失败——那几次里
没有一次会成功，因为错误在第一次就已经确定不会变。

`isRetryableJobError`（`internal/app/pipeline.go` 第 273–329 行）把 4xx（排除 408/429，这两个
会自己变好，仍然走退避）判定为不可重试，直接判永久失败。它靠 `errors.As` 在错误链里找
`*common.StatusError` 来做这个判断，而这个判断能生效，靠的是错误链没有被压扁成一个纯字符串。
`redactError`（`internal/app/provider_channel_runtime.go` 第 1039–1065 行）以前是把整条错误用
`errors.New` 拍平成一个新字符串，`errors.As` 在这样的错误里什么都找不到，于是无论错误本身
是不是确定性的 4xx，都会被当成"可能重试就好了"走完整条退避链。现在的做法是把状态码和已经
脱敏过的响应体重新拼成一个新的 `*common.StatusError` 塞回链里：`errors.As` 照样能找到它去
分类，但脱敏后的文本里不会残留 Key（`redactString`，同文件第 1066–1069 行）。

**这条规则现在还有第二个例外**：401/402/403 也不再直接判永久失败——`isRetryableJobError`
会额外问一次 `providerpool.ClassifyFailure`，命中 `MemberSpent` 就当作可重试。原因不是这三个
状态码本身值得重试，而是「Key 耗尽自动退休」一节说的那件事已经在更早一层发生过了：
`Pool.complete` 已经把出这个错的 member 标记退休，下一次尝试会自然换到别的 member，所以重试
在这里换来的是另一把 Key 的结果，不是对同一把死 Key 的重复拍打。这跟本节开头「4xx 重试也没用」
的说法看起来矛盾，其实是两条判断分工：`*common.StatusError` 的状态码本身决定"这个 4xx 是不是
确定性的"，`ClassifyFailure` 再决定"确定性的失败要不要因为下一次会换一把 Key 而值得再试一次"。

之所以要"重新拼"而不是直接用 `%w` 包一层原始错误——那样更省事——是因为
`*common.StatusError.Body` 装的是上游服务器原样返回的内容：一个转发服务如果把请求原文回显进
错误信息（有的确实会这样），Key 就会连着这个 Body 一起原样保留在错误链里，最终写进
`jobs.last_error_message`，落进数据库和 `/progress` 页面。重新拼出的 `StatusError` 里，`Body`
永远是脱敏之后的文本，Key 没有机会跟着这条链走到任何地方。

## 两把 Key 不能同名

不管是新建通道，还是往已有通道里加一把 Key，两个 member 想用同一个名字都会被直接拒绝，错误
信息里会点名是哪个名字重复了，而不是数据库那句看不懂的约束报错。

Schema 层面这从没变过：`provider_channel_members` 表自 migration 0013 起就有
`UNIQUE(channel_id, label)`（`internal/repository/sqlite/migrations/0013_v015_capture_provider_channels.sql`
第 116 行）。以前提交重复名字时，这条约束照样会拦下写入，但拦下之后往外抛的是 SQLite 原始的
报错文本，不会点名到底是哪个名字撞了。现在创建通道（`SaveProviderChannel`，
`internal/app/service.go` 第 309 行）和修改通道（patch 分支，
`internal/app/provider_channel_operations.go` 第 179 行）都在真正写入任何东西之前，先调用同一个
检查函数（`validateDistinctProviderChannelMemberLabels`，
`internal/app/provider_channel_operations.go` 第 62–72 行）。被拒绝的提交不会碰到 secret store，
也不会在数据库里留下任何痕迹——检查在写入之前就挡住了，不是写完再回滚。

## 报错只报到能报的那一层

这是"Key 永不离开 Hub"那条边界在另一层的延续：provider channel 的写接口现在只把校验失败的
文字原样显示给操作者，其它层——存储、密钥——出的错不会原样显示。

新建通道的接口以前把 `err.Error()` 原样塞进 HTTP 响应，而 `SaveProviderChannel` 会依次碰到
SQLite 和 secret store 两层，任何一层出的错都会这样被原样回显——重复名字曾经就是这样把
`UNIQUE constraint failed: provider_channel_members.channel_id, ... (2067)` 这类数据库内部文本
发到浏览器里的。修改通道的接口有相反的毛病：以前把所有失败都收成同一句通用提示，点名重复
名字的那句话永远传不到出错的操作者手里。现在两个接口都只在错误包着
`app.ErrProviderChannelValidation` 这个哨兵错误时，才把错误文字写进响应；其它一律换成一句
不带内部信息的通用提示（创建分支，`internal/api/server.go` 第 354–361 行；更新分支，同文件第
391–397 行）。那条边界管的是 Key 本身不能出现在错误文本里；这一条管的是错误文本本身有没有
资格被显示出来——两条边界形状相同，只是管的层不一样。
