# Timingdex v0.16: Worker Provider Modes and Operations

## Choose a Provider path

| Mode | Use it when | What crosses the Hub | Key exposure |
| --- | --- | --- | --- |
| Hub proxy | The Worker is trusted to process media but must not see a Provider key | JSON API request/response only, max 2 MiB | Hub memory only |
| Worker direct | The Worker is a trusted, controlled machine and Provider uploads should not consume NAS Hub bandwidth | Task credential control request; the Worker calls the Provider directly | Worker memory during the task |

The proxy rejects multipart, video, audio and image requests. It is not a
transport for NAS originals, proxies, thumbnails or audio. The direct route
lets the Worker send material to the selected Provider without first pushing it
through the NAS Hub.

Enable direct mode only for a paired device you control:

```json
{
  "hub_security": {
    "allow_worker_provider_credentials": true
  }
}
```

or set `TIMINGDEX_ALLOW_WORKER_PROVIDER_CREDENTIALS=true` for the Hub process.
The default is `false`. A Worker must own the live job lease and declare the
requested `provider_operations` capability. The Hub records worker, job,
provider, operation and expiry, never the key itself. The expiry does **not**
revoke the Provider’s upstream API key; rotate or revoke the paired Worker if
the machine is lost.

Declare only the operations the node is allowed to run at enrollment time:

```sh
timingdex worker enroll ... --provider-operation video_analysis \
  --provider-operation asr
```

The shipped `timingdex worker run` executes the media-derive stage. The direct
and proxy methods are the guarded transport contract for a compatible Worker
Provider executor; dispatching Provider-native video/ASR payload generation
and result commit remains a separate workflow step rather than pretending that
an API key endpoint alone performs analysis.

## Operating the Hub

- `/providers`: create, edit, test, enable, disable or remove a channel. A
  removed channel is disabled and its Hub secret is cleared; API responses do
  not expose a key or secret reference. **This is a separate configuration
  path from the Provider modes above**: Hub proxy and Worker direct both
  resolve a Provider from `providers.*` (`config.json`/env) only, never from
  a channel, even an enabled one with a healthy member — see [v0.21 Provider
  deployment](v0.21-provider-deployment.md) for why that boundary exists. A
  capability configured only through `/providers` still needs its own
  `providers.*` entry before a Worker can reach it in either mode; the
  refusal a Worker gets otherwise now distinguishes "nothing configured" (503)
  from "configured, but only as a channel" (403) instead of both reading, at
  a flat 400, like the channel setup itself is wrong.
- `/workers`: enter the Hub admin token only for the current page, inspect
  mounted roots/capabilities, stage/progress, retry cause and node assignment.
  “Preferred” is a soft hint; “Specified” prevents another Worker from leasing
  that derive job.
- `/`: filter by processing state and choose a saved Collection. Collections
  store only date, coarse region, camera, session and status filters—never
  source paths, coordinates or credentials.

## Required real-machine smoke test

1. Pair one Windows/Linux x64 Worker and one ARM64 Worker; verify certificate
   fingerprint pinning and each declared mount.
2. Run one proxy derivation on each; verify progress, artifact upload and
   offline recovery on `/workers`.
3. In proxy mode, make a small JSON Provider request and confirm the Worker
   has no Provider key in its config or process logs.
4. In direct mode, use an isolated test key, confirm the Worker sends to the
   Provider without Hub media relay, then rotate that key.
5. Confirm failed, queued and ready material appears under the library status
   filter and a saved Collection returns the same safe browse set.
